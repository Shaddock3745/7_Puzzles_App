# 詢答題庫：決賽（7 分鐘）

> 2026-10-31 初稿。評審是鈦坦邀的業界人士，評**適應性 40／可視性 30／技術性 30**。
> **他們想知道的是「這個人怎麼做事」**，不是演算法多厲害。所以每題的答案都往流程、判斷、證據靠，數字只當佐證，**不主動講演算法**；被追問技術細節再講，講完拉回「所以我們怎麼決定」。
>
> 每題四格：**他其實想知道什麼**（題目背後的擔心）／**建議答法**（口語、30 秒內講得完，第一句就是結論）／**證據**（可以指講義或打開給他看的東西）／**地雷**（別這樣講）。
> ⚠️ 標「你確認」的是我不知道、要你自己填的事實。答法是草稿，**照你自己的話改**，背的話聽得出來。
>
> 講義上的位置：正面 ① 流程、② 適應性；背面 ③ 可視性、④ 技術性。

## 一、AI 程式助理（最可能先問、問最深）

業界現在每家都在導 AI 寫程式，他們真正擔心的是：**品質誰負責、人有沒有被架空、出錯怎麼抓得到**。這組答得好，其他都加分。

### 1. 程式是 AI 寫的，那你做了什麼？

| | |
|---|---|
| 他想知道 | 你是開發者還是傳話的人；功勞算誰的 |
| 答法 | 「方向和架構是我決定的，實作交給 AI 程式助理。我守兩道關：寫程式之前，它先用中文寫出這張卡要記住什麼、做什麼、遇到什麼情況怎麼辦，我確認了才准動手；寫完之後，我在實機上玩過才算完成。決定做什麼、不做什麼，全部是我。」 |
| 證據 | 講義正面「流程五步」；舉一個**你推翻它**的例子（下一題） |
| 地雷 | 不要說「AI 只是輔助」來淡化——每個 commit 都有 `Co-Authored-By: Claude`，淡化反而像藏。照實講分工，重點放在「關卡是人守的」 |

### 2. 舉一個你推翻 AI 建議的例子

| | |
|---|---|
| 他想知道 | 第一道關卡是不是真的有在擋，還是蓋章 |
| 答法（挑一兩個你最有感的） | ① **拍照出題的評分基準**：原本拿我們自己拼的造型題測，成績很好看；我判斷那本來就拼得出來、太好考，改成用公開的生活物品資料集，標準一下子嚴很多。② **選題畫面**：原本拍完直接進關，我改成先列幾個候選讓玩家自己挑，演算法的「廢案」變成選項。③ **「拼到一半提醒」這個功能**：評估成本之後是我拍板不做。④ 協作方式本身：它一度以為「它只做 review、我自己寫」，我直接更正流程 |
| 證據 | 講義正面 A、C 那兩格 |
| 地雷 | 不要舉「它寫錯一個變數我抓到」這種小事——要舉**方向上的判斷** |

### 3. AI 寫的程式品質怎麼保證？它寫的測試會不會只是自己驗自己？

| | |
|---|---|
| 他想知道 | 你懂不懂「測試也可能是假的」這件事 |
| 答法 | 「三層。第一，寫之前中文邏輯先過我這關，錯的方向不會進來。第二，590 個自動化測試，每次 push 自動跑。第三，我們做過變異測試：故意把程式改壞，確認指定的那一條會變紅——測試抓不到的話，那條測試就是假的。手指拖曳那一層沒有自動化測試，靠實機玩過才能進完成欄。」 |
| 證據 | 講義背面 ④ |
| 地雷 | 不要說「測試全過所以沒問題」。主動講出沒測到的那一層，比假裝全覆蓋可信 |

### 4. AI 出過錯嗎？你怎麼發現的？

| | |
|---|---|
| 他想知道 | 你有沒有獨立判斷的能力 |
| 答法 | 「有。例如拍照出題的驗收工具，成績一直偏低，是我看圖發現每隻貓都只剩身體——工具在形狀最細的地方把外框切斷了，只量到最大的那一塊。數字看不出來，要人看圖才看得出來。還有一次桌機版一開就讓顯示卡當掉，它一開始判斷是驅動不穩，後來開除錯工具查到是 Unity 引擎本身的問題，第一個判斷是錯的。這些都寫進除錯記錄，每則都記『怎麼發現的』和『失敗的嘗試』。」 |
| 證據 | 講義背面「16 則除錯記錄」 |
| 地雷 | 不要講成「AI 很爛」或「AI 很神」，講成「出錯是常態，所以流程要抓得到」 |

### 5. 你看得懂它寫的程式嗎？

| | |
|---|---|
| 答法 | 「看得懂，這是我給自己的規矩：程式讀懂才往下一張卡。所以中文邏輯那一關不只是批准，也是我先理解它要怎麼做。」 |
| ⚠️ 你確認 | 要不要舉一個「讀程式時發現問題」的例子 |

### 6. 用 AI 花了多少錢？值得嗎？

| | |
|---|---|
| 答法 | 「唯一的開銷是 AI 程式助理的訂閱，NT$4,312，其他工具都是免費方案。值不值得：一個人兩個多月做到 590 個測試、有 CI、有完整文件，沒有它做不到這個範圍；但方向錯了它也會很有效率地做錯，所以人守的那兩道關才是重點。」 |

## 二、敏捷流程是不是真的（適應性 40、可視性 30）

他們看過很多「名義上敏捷」的專題。要用**具體的一次轉向**證明流程真的有在改計畫。

### 7. 一個人做，為什麼要敏捷？跟一般寫完再測有什麼不一樣？

| | |
|---|---|
| 他想知道 | 你是真的需要它，還是為了得獎套上去 |
| 答法 | 「因為很多設計一開始猜不準。例如『拼到一半提醒玩家』，動手前先寫測試檢查做法，392 個擺法只有 41 個符合假設，就知道這條路行不通——如果是先寫完再測，這個要到最後才發現。敏捷對我來說就是：**把會被推翻的假設提早拿去撞**。」 |
| 證據 | 講義正面 A |

### 8. 為什麼選看板，不選 Scrum？

| | |
|---|---|
| 答法 | 「一個人沒有每日站會的對象，而且演算法的工作很難估到兩週一個衝刺。所以不排固定週期，做完一張拉下一張；但用階段切大目標，一個階段開一張看板，像打地基、做原型、出題與難度、決賽準備，各自有完成條件。」 |
| 追問：WIP 上限？ | ⚠️ 你確認：有沒有刻意限制同時進行中的卡。如果沒有正式上限，照實講「沒設數字，實務上是做完一張才拉下一張」 |

### 9. 「完成」的定義是什麼？

| | |
|---|---|
| 答法 | 「三件事：自動化測試全過、文件更新到唯一的那一份、**實機玩過**。看板上特別多一欄『測試中』，沒在手機或平板上玩過不能進完成。」 |
| 證據 | 講義正面看板四欄 |

### 10. 時程估得準嗎？

| | |
|---|---|
| 他想知道 | 你會不會追蹤計畫與實際的差距，還是只畫好看的甘特圖 |
| 答法 | 「演算法那個階段大多比預定早完成。重點是預定訂了就不改，只補實際，所以差距看得到。提前空出來的時間，我拿去找 11 個人試玩——那不在原本的計畫裡，但比照計畫往下做更有價值。」 |
| 證據 | 講義背面甘特圖（橘色那條「不在規劃：找人試玩」） |
| 地雷 | 不要說「都有照計畫」。偏差本身是好證據 |

### 11. 有做回顧嗎？哪一次回顧改變了做法？

| | |
|---|---|
| 答法 | 「沒有固定週期的回顧會議，回顧落在兩個地方。一是每次踩到不報錯的怪問題，就寫一則除錯記錄，最後寫成規則，每次開工先讀。二是決賽前拿評分表回顧，發現少了持續集成，當週就補上。」 |
| 證據 | 講義背面 ④ 最後一條 |
| 地雷 | 不要硬說有 sprint retrospective |

### 12. 使用者回饋只有兩輪、第二輪才一個人，算「頻繁」嗎？

| | |
|---|---|
| 他想知道 | 你會不會誇大 |
| 答法 | 「照實說，不算頻繁，這是這次做得不夠的地方。第一輪 11 個人，推翻了兩個定案；第二輪只找到一位，但他在決賽用的平板上玩，5 條發現每條都有處置，3 條在凍結前改好。如果重來，我會固定每個階段結束就找人玩一次，不要等到報名前。」 |
| 證據 | 講義正面 B 兩格 |
| 地雷 | 不要把一位講成「使用者們」 |

### 13. 怎麼決定一個功能要砍？

| | |
|---|---|
| 答法 | 「看三件事：做法有沒有被證明可行、還剩多少時間、砍掉之後產品缺不缺。『拼到一半提醒』前兩項都不利，而且砍掉之後還有『提示下一片放哪』可以頂。從開卡到決定不做 47 天，中間延過一次——**延和砍都是有紀錄的決定**，不是忘記做。」 |
| 證據 | 講義背面進度圖上的 47 天括號 |

### 14. 決賽報告為什麼跟初賽差這麼多？

| | |
|---|---|
| 答法 | 「因為只入圍這個獎，評的是怎麼做出來的，所以公布隔天就把報告主角從演算法換成開發過程。這也是一次照證據改計畫。」 |

### 15. 進度別人怎麼看得到？

| | |
|---|---|
| 答法 | 「看板在 GitHub 上，每張卡連到對應的 commit；進度圖是從看板資料畫的，不是手填的。文件規定每件事只寫在一個地方，別處只放指標，所以不會有兩份互相矛盾。協作者完全靠交接文件跟我對接。」 |
| 證據 | 講義背面 ③ |

## 三、品質與工程實務（技術性 30）

### 16. CI 做了什麼？有 CD 嗎？

| | |
|---|---|
| 答法 | 「每次 push，GitHub Actions 在 Windows 主機上跑全部 590 個測試，結果直接標在 commit 旁邊。打包和裝到平板目前是手動的，沒有自動部署——遊戲引擎打包需要授權和比較重的環境，這次沒做，是下一步。」 |
| 地雷 | 不要把 CI 講成 DevOps 全套 |

### 17. 為什麼 CI 這麼晚才加？

| | |
|---|---|
| 答法 | 「一開始測試就是在引擎外幾十秒跑完，我每次改完都手動跑，所以沒感覺到缺。拿評分表回顧才意識到：手動跑靠的是我記得跑，CI 是不靠人記得。發現缺口當週補上。」 |

### 18. 遊戲的畫面和操作沒有自動化測試，怎麼防回歸？

| | |
|---|---|
| 答法 | 「架構上把規則和畫面分開：幾何、出題、難度、實力全在不依賴引擎的那一層，那層有自動化測試。畫面那層靠『測試中』這一欄的實機試玩，加上除錯記錄把踩過的坑變成檢查規則。這是已知的缺口，不是沒想到。」 |

### 19. 展示版和正式版怎麼管？會不會不小心把展示設定出貨？

| | |
|---|---|
| 他想知道 | 設定管理、環境差異（業界很常出事的地方） |
| 答法 | 「『是不是展示版』只在一個地方定義，靠一個編譯開關決定。監控面板、實力變化放大十倍、清除紀錄鈕，全部問同一個地方。沒加開關打包出來的就是正式版，三樣一起消失，不會只漏一樣。」 |

### 20. 技術債怎麼處理？

| | |
|---|---|
| 答法 | 「待辦清單裡有一區專門放技術債，知道但這次不還的寫清楚為什麼。功能凍結之後只修 bug，不再加東西。」 |

### 21. 最大的一次踩坑是什麼？

| | |
|---|---|
| 答法 | 「桌機版一開就讓顯示卡驅動逾時。查到最後是引擎在新的繪圖介面上有 bug。修法是換回舊的繪圖介面——**刻意不升級引擎**，因為比賽期間升級的風險比這個 bug 大。這種『知道根因但選擇繞過』的決定也寫進記錄。」 |
| 證據 | 除錯記錄 011 |

## 四、團隊與協作

### 22. 協作者怎麼分工、怎麼對接？他沒交東西怎麼辦？

| | |
|---|---|
| 他想知道 | 依賴管理、介面設計、溝通 |
| 答法 | 「他中途加入，負責影像辨識，所以另外開一張看板。對接只約定一個介面：照片進去、輪廓出來，寫在交接文件裡。我先用一個假的辨識模組開發，所以不會被他卡住；他交件那天，換一行就接上了。接上時還是出過一次問題——座標的上下方向兩邊理解不同，整隻貓顛倒——之後就把這條寫進介面的說明裡。」 |
| 證據 | 講義正面「協作者」那張看板；除錯記錄 015 |
| 地雷 | 不要說「他還有幾張沒交我們不管」——講成「設計上不依賴他的進度」 |

### 23. 如果團隊變成五個人，你這套流程還能用嗎？

| | |
|---|---|
| 答法 | 「核心可以直接擴：看板、『測試中』要實機玩過、文件單一來源、CI。要加的是程式碼審查——現在中文邏輯那一關是我一個人在審，五個人就要變成合併前的 review，CI 綠燈當合併條件。」 |
| ⚠️ 你確認 | 分支策略照實講：目前主要直接在 main 上開發，協作者在自己那份做完再合進來 |

## 六、反思（幾乎一定會被問一題）

### 27. 重來一次會改什麼？

挑兩個你真心認同的講，不要全講：

- **更早找真人**：第一輪回饋推翻了兩個定案，越早撞到越便宜
- **一開始就上 CI**：成本一小時，卻拖到決賽前才補
- **回饋排成固定節奏**：每個階段結束就找人玩，而不是有空才找
- **輸入層也做自動化測試**：現在全靠實機，回歸成本高

### 28. 這次最大的收穫？

⚠️ 你自己的話。可以從這個方向想：「學到怎麼把判斷留給自己、把執行交出去」或「學到證據比直覺可靠，包括證明自己錯」。

## 七、萬一被追問技術

| 被問 | 一句話，講完拉回流程 |
|---|---|
| 題目怎麼保證有解？ | 先把七片拼好再描外框，答案在出題時就存在。→「所以這條不用測試去追，是架構保證的」 |
| 難度怎麼算？ | 外框形狀的六個特徵加權，權重寫在設定檔。→「11 個人的試玩驗證過，結果沒有拿來調權重，所以是驗證不是擬合」 |
| 實力怎麼算？ | 西洋棋等級分（ELO）：看花多少時間、用幾次提示。→「展示版變化放大十倍，評審玩兩三題就看得到」 |
| 拍照怎麼變成題目？ | 辨識出輪廓，在所有拼得出來的擺法裡找最像的。→「所以一定拼得出來，只是有時不夠像，這也是讓玩家自己挑的原因」 |
| 為什麼不用生成式 AI 出題？ | 出題要保證有解、難度要能重算，生成式做不到這兩點。開發用 AI 是另一回事 |
