# 開發須知

> 動程式之前先讀這份：設計鐵則、儲存契約、命名規則、測試方式、常見陷阱與開發環境的限制。
> 規格與設計理由在 `文件/規格/`：模型層看 `七巧板儲存規格.md`，互動層看 `互動設計.md`，
> 每支程式的 API 與「為什麼這樣設計」看 `程式說明書.md`。

---

## 這是什麼專案

Unity 6000.3.7f1 的**七巧板拼圖遊戲**「巧級 Tangrade」，2026 大專校院資訊應用服務創新競賽參賽作品。

核心不是遊戲本身，是「把難度與玩家實力量化成可驗證的系統」：演算法即時生成題目、特徵函數算難度、ELO 換算玩家實力，三者互相驅動。**不用生成式 AI、不連網。**

題目呈現是「盒子」，不是自由拼：玩家填滿盤面上一個固定位置的容器，吸附有硬限制（只能吸在盒內、不能重疊），所以**過關判定就是 `LevelData.MarkSolvedIfAllOnBoard()`**——七片都合法放置就必然填滿（面積 32 = 盒子面積）。完整規格見 `互動設計.md`。

**所有程式檔都有 XML doc**（`<param>` / `<returns>`），IDE 的提示視窗會顯示。「這個參數是什麼」直接看程式碼，`程式說明書.md` 講的是「為什麼這樣設計」。

## 三條鐵則（破了會出現最難查的 bug）

### 一、浮點永遠不進模型

座標型別是 `Scalar`（`n + m√2`，兩個 `long`），不是 `float`。手指位置這類浮點值一律先過 `SnapSolver` 轉成精確座標才能進 `BoardState`。

「兩個點是不是同一點」是整數比較，不是容差判斷。七巧板大量出現點接觸與邊貼合，用容差會很痛。

### 二、節點索引不可更動

每片的節點順序由 `PiecePrototype` 沿 CCW 邊界走訪產生，`Arrangement.Links` 存的就是這個索引。**改了原型頂點或節點產生順序 = 資料庫裡所有的解全部失效，而且不會報錯。**

### 三、只存相對編碼，座標需要時重算

`Arrangement` 只存七片的 `Rotation`/`IsFlipped` 加六條連接，不存座標。頂點、輪廓、絕對座標一律不入庫。

## 儲存契約：這三樣改了，已存的檔案全部失效

鐵則二只講了三樣裡的一樣。**開始存題目之後，下面每一樣都跟它同一個等級**——
改了不會報錯，只會讓資料庫裡的東西安靜地對不起來。

| # | 什麼 | 改了會怎樣 |
|---|---|---|
| 1 | **`PiecePrototype` 的節點產生順序**（＝鐵則二） | `Arrangement.Links` 存的就是這個索引 → 所有的解全部失效 |
| 2 | **`Serialization` 的 DTO 欄位名與片種字串**，以及 **`PlayerProgress` 的欄位名**（玩家手機上的進度存檔） | `FromDto` 要嘛丟「未知的片種」，要嘛**把欄位讀成預設值**（`JsonUtility` 對不認得的欄位不吭聲）——後者是靜默的。進度存檔的 `formatVersion`／`skillRating` 讀成 0 會被當壞檔（玩家的實力回到起點），其他三個安靜地變成預設值 |
| 3 | **`BoundaryTracer` 的追邊行為** | `PuzzleKey` 是從它的輸出算的 → **所有題目的 key 全部變號**，`puzzleKey` 的指向整批斷掉。追邊行為已經凍結，不要再改 |

💡 **字串長什麼樣**：`LARGE_TRIANGLE` / `MEDIUM_TRIANGLE` / `SMALL_TRIANGLE` / `SQUARE` / `PARALLELOGRAM`，
欄位是 `rotation` / `flipped`。`七巧板儲存規格.md` 已改成對齊程式（早期版本寫 `LARGE_TRI` / `rot` / `flip`），
理由在那份文件 §1 裡——簡單說：規格原本的 `links` 格式 `JsonUtility` 序列化不出來，而縮寫違反下面的命名規則。

## 命名規則

**識別字一律用完整單字，不縮寫**（`triangle` 不寫成 `tri`、`direction` 不寫成 `dir`、`length` 不寫成 `len`），也不用 `temp`/`tmp` 這類名稱。型別、方法、參數、區域變數都適用。

**例外**：`for` 迴圈的 `i` / `j` / `k` 可以。

專案已經全面改過一輪，新程式照這個規則寫。

## 怎麼跑測試

Unity 內：**Window → General → Test Runner → EditMode → Run All**。

**更快的方法是用 `dotnet` 在 Unity 外面跑**——秒級回饋，不用開 Unity。

測試專案就在 repo 裡：`Tools/DotnetTests/`（路徑全是相對的，換電腦不用改）。

```bash
dotnet test Tools/DotnetTests
```

裡面兩個檔案：

- `tests.csproj` —— 用 `../../Assets/Scripts/Data/*.cs`、`../../Assets/Scripts/Core/*.cs`、`../../Assets/Tests/EditMode/*.cs` 三行把原始碼拉進來
- `UnityStub.cs` —— 補上 Unity 的相依（只用到 `Vector2` 與 `JsonUtility`）

**`UnityStub.cs` 一定要放在 `Assets/` 外面。** 放進 `Assets/` 的話 Unity 會一起編，`UnityEngine.Vector2` 就會有兩份定義。`Tools/` 在 `Assets/` 外，Unity 完全不會看它。

`bin/`、`obj/` 已經在 `.gitignore` 裡。

`GameObject/`、`Editor/`、`Recognition/` 三層要 Unity 才編得到，`dotnet test` 跑不到；`Recognition/` 的測試（`Tangram.Recognition.Tests`）要在 Unity 的 Test Runner 跑。

**持續集成**：`.github/workflows/tests.yml` 在每次 push 時用 GitHub 的 Windows 主機跑**同一條** `dotnet test Tools/DotnetTests`，結果是 commit 旁邊的綠勾／紅叉。改測試專案（套件版本、路徑）時兩邊一起看；`[Explicit]` 的工具不在裡面跑。

**NUnit 一定要 3.x**（Unity 用 3.x；NUnit 4 拿掉了 `Assert.AreEqual` / `Assert.IsTrue`，會編不過）。

⚠️ **而且要釘在 3.6.1，不要升級**。Unity 帶的是**客製的 NUnit 3.5**（`com.unity.ext.nunit`），
dotnet 這邊如果用較新的版本（例如 3.14），`Is.AnyOf` 這類 3.5 之後才加的 API 在 dotnet 全綠、**到 Unity 才編不過**。
3.5 本身沒有 .NET Standard 版本，在 net10 下編得過但跑不起來，**3.6.1 是最接近而且跑得動的**。
症狀是「dotnet 全過、Unity 報 CS0117」，看到就是這個原因。

⚠️ **`NUnit3TestAdapter` 也要釘在 3.17.0**。4.x 的 adapter 配 NUnit 3.6.1 時 **`--filter` 完全沒作用而且不報錯**：
不管怎麼寫都照跑全部、`[Explicit]` 一條都不跑（推測是 3.6.1 看不懂 adapter 4.x 送過去的篩選格式）。
Unity 不用這個 adapter，所以對 Unity 沒有影響。
⚠️ **換 adapter 版本之後要刪 `Tools/DotnetTests/bin/Debug` 與 `obj`**：舊版的 dll 留在輸出資料夾裡，症狀是「tests.dll 中未提供任何測試」。
沒換版本也可能撞到（輸出裡有 `testcentric.engine.metadata` 的警告，那是 4.x adapter 留下的東西），刪掉同樣兩個資料夾就好。

### 怎麼跑 `[Explicit]` 的工具

**`--filter` 選不到 `[Explicit]` 的測試**（3.17 也一樣，回「沒有符合的測試」）。要用 **NUnit 自己的篩選**：

```bash
dotnet test Tools/DotnetTests -- "NUnit.Where=name == RescaleDifficultyWeights"
```

| 工具 | 英文入口（`ExplicitTools`） | 原本的名稱（中文也跑得動） |
|---|---|---|
| 改權重之後的重算（**會寫權重檔**，約 40 秒） | `RescaleDifficultyWeights` | `尺度_權重改過之後重算換算倍率` |
| 生成時間表（Debug 十幾分鐘） | `GenerationTimeTable` | `生成時間_幾個目標各生一百題` |
| 批次統計（約 20 秒） | `BatchStatistics` | `批次統計_一千題的特徵分布量得出來` |
| 縮圖牆匯出（約 35 秒） | `ExportThumbnailWall` | `縮圖牆_匯出兩千個形狀` |
| 求解器完整驗證＋解數表（Debug 約 2 分半） | `SolverTable` | `求解器_全部形狀驗證並印出解數表` |
| 逼近搜尋驗收：25 個具象題＋掃描樣本，對照與實驗兩組並排，另外匯出 `%TEMP%\tangram_approximation.html`（Debug 約 3 分鐘） | `ApproximatorTable` | `逼近_具象題與掃描樣本的成績表` |

⚠️ **窮舉這類重計算在 Debug 比 Release 慢大約 13 倍**（求解器量的）。`dotnet test` 與 Unity 的 Test Runner 都是非最佳化模式，
所以**日常測試只放便宜的形狀**，完整的放 `[Explicit]`。要量「實際有多快」請另開 Release 的主控台程式，不要看測試的耗時。

💡 英文入口只是方便（短、不用切輸入法），中文名稱在 Git Bash 與 PowerShell 都驗過跑得動。
`--filter` 篩不到 `[Explicit]` 的測試，原因是 `[Explicit]`，不是中文名稱；
非 `[Explicit]` 的測試用 `--filter "FullyQualifiedName~中文名稱"` 照常篩得到。

⚠️ **印出來的報告要加 `--logger "console;verbosity=detailed"` 才看得到**，不加只會看到一行「已通過」。

**動到 Data 層一定要重跑全部測試再往下走。**

## 容易踩的坑

| 坑 | 說明 |
|---|---|
| **`Placement.Equals` 是姿態相等，不是形狀相等** | 正方形 `Rotation = 0` 與 `= 2` 佔位一模一樣但不相等。要問「是不是同一件事」用 `Canonical`；要比幾何位置比頂點集合 |
| **`PiecePrototype.Get()` 回傳共用單例** | 裡面的陣列改下去會污染全域 |
| **`Placement.Vertices()` 在 flip 時反轉寫入順序** | 目的是**把繞向正規化回 CCW**，所以輸出**永遠是 CCW**（測試 `翻轉後繞向重新正規化` 釘住，五種片 × 8 旋轉 × 翻面全驗）。代價是索引對應會變：翻面時 `Vertices()[i] == ToWorld(Prototype.Vertices[n−1−i])`，所以 `Vertices()[0] != ToWorld(Prototype.Vertices[0])`。`Nodes()` 刻意不做這個反轉（節點索引是儲存契約） |
| **背面剔除吃掉翻面的平行四邊形** | 這個坑**跟 `Vertices()` 無關**（它永遠 CCW，三角化不用吃兩種繞向）。真正的來源是用 `transform.localScale.y = -1` 做翻面——負縮放會反轉繞向，背面剔除就整片消失。要嘛不用負縮放（重新產生 mesh），要嘛材質設 `Cull Off` |
| **`Scalar.MultiplyByHalfRoot2()` 的偶數 assert 不要拿掉** | 45° 旋轉的封閉性檢查 |
| **SAT 中距離 0 算「分離」** | 只有內部交集才算重疊，否則邊貼合與點接觸全誤判 |
| **共線邊只在邊界度數 = 2 時合併** | 捏點度數是 4，合併會毀掉拓樸 |
| **`Canonical.PuzzleKey` 要跑 16 次輪廓追蹤** | 不便宜，算過就存起來。盒子模式下遊玩迴圈已經不用它了 |
| **`Serialization.FromDto` 不重算 key** | 相信檔案裡存的 |
| **繪製順序：先 sorting layer 再 order** | 層清單在 `ProjectSettings/TagManager.asset`（`Box → Piece → ScanPhoto → GameUI → CompleteUI`；`ScanPhoto` 是照片對照用的，**要在 Unity 的 Tag Manager 手動建**，`ScanPhotoView` 啟動時會檢查；提示覆蓋片刻意**不另開層**，住在 `Piece` 層、order 夾在未吸附與拖曳中之間，拖著的片才壓得過它），層名常數在 `PieceSorting`。**跨系統的先後由 layer 決定，order 只在自己那層裡有意義**。<br>新增任何會生 renderer 的東西時**記得設層**——沒設會留在 `Default`，症狀是**被別的東西蓋住而且不報錯**。也不要靠「挑一個夠大的 order」壓過別人，那不是排序是巧合 |
| **`Region.ContainsPolygon` 只管出界，不管重疊** | 合法擺放要它與 `Geometry.ConvexOverlap` 兩個都過 |
| **`Region` 內部有兩套座標系** | 原座標與 ×2。中點只在 ×2 那邊算，混用會差一個 2 倍而且不報錯 |
| **兩個地方各自認定「真相」= 安靜的 bug**（`PiecePreview` 的教訓） | `PiecePreview` 每幀無條件把 `Rotation`/`IsFlipped`/`IsSnapped` 蓋回 Inspector 滑桿值，而控制器也在寫——症狀是「旋轉鈕按了完全沒反應」，不報錯。`PiecePreview` 後來已刪除。<br>**判準不是「誰寫哪個欄位」**——`TrayView` 與控制器都會寫 `IsVisible`，那沒問題，因為真相只有一份（`LevelData`），控制器只是在改完真相的同一刻順手同步。新增任何會碰 `PieceView` 的東西時先問：**這個欄位的真相在哪？我是在改真相，還是在畫真相？** |
| **手感的單位是 dp，不是螢幕像素** | 像素不是穩定單位——18 px 在 1080 寬的手機是 1.7% 螢幕寬，在 2160 寬的平板只剩 0.83%，**同一個數字手感差一倍**。換算走 `ScreenMetrics`（1 dp = 1/160 英寸）。<br>**Editor 與桌機版（exe）一律用基準密度 400 dpi**，不讀 `Screen.dpi`——那支在電腦上回的是螢幕的 dpi（約 96），會讓「在 Editor 調好的手感」到別的地方完全不成立。**只有手機版讀真實 dpi**。<br>它跟 `CanvasScaler`（照解析度比例）**不是同一套**，手機上接近、平板上會分家 |
| **`BoardView.SnapSettings` 是在版面重算那一格算好存起來的** | 而版面重算**只在螢幕尺寸變了才跑**。所以 Play 模式下改 Inspector 的吸附／脫離半徑**不會即時生效，而且不報錯**——要重進 Play。調參期間可以臨時改成現算，調完記得改回來 |
| **`MonoBehaviour` 不可以停用自己所在的物件** | 它會連自己的 `Update` 一起關掉，而且**完全不報錯**。症狀是「這個東西第一次隱藏之後就再也不出現」（例如 undo 鈕）。要開關某個東西的邏輯，必須住在**不會被它自己關掉**的地方——`PieceActionButtons` / `BoardActionButtons` 都是獨立的管理物件，就是這個原因 |
| **「隱藏就不擋」是一條會被拿來用的機制，不只是防呆** | 擋片區跳過停用的物件（`activeInHierarchy`）。所以按鈕蓋住抽屜縮圖的解法是**讓按鈕隱藏**，不是改判定順序。反過來說，任何「只關掉圖片、物件還開著」的隱藏做法都會留下點不到片的死角 |
| **`LevelData.SetInTray` 對還在盤上的片會丟例外** | 那是刻意的。「在盤上」與「在待用區」互斥，默默修正的症狀是「片在抽屜裡但盤面認為它還在盒內」——過關判定跟著錯，不報錯。所以回收那條一定是**先 `Lift` 再 `SetInTray`** |
| **`Pointer.current` 在手機上只反映主要觸控** | 第二根手指之後完全看不見。症狀是「手掌先碰到螢幕就整個沒反應」，而且**在 Editor 用滑鼠永遠測不到**。輸入層已改成按下時鎖定 touch id、之後只聽那一根（`互動設計` §15.5）。新加輸入路徑時不要退回去直接讀 `Pointer.current` |
| **UI 的螢幕位置一律走 `UiScreenRect`，不要用畫布的相機換算** | 畫布是 **Screen Space - Camera**，相機被 `BoardView` 改過的那一幀畫布還沒跟上（要到 `willRenderCanvases` 才跟上），`RectTransformUtility.WorldToScreenPoint`／`RectangleContainsScreenPoint` 配畫布的相機會算錯。盒子區又是照按鈕排算相機的 → **回授迴圈，盒子連抖十幾幀**、正在拖的片被放回原位，不報錯。`UiScreenRect` 用根畫布的本地座標換算、完全不讀相機，**前提是根畫布蓋滿整個螢幕** |
| **`EventSystem.IsPointerOverGameObject()` 會晚一幀** | 它的答案由 UI 輸入模組在**它自己的 `Update`** 裡算，而 `MonoBehaviour` 之間的順序是未定義的——按下那一幀很可能拿到上一幀的答案，症狀是「按按鈕的同時也抓到了片」，時好時壞且不報錯。`TouchInputController` 改成自己比矩形（`RegisterPressBlockingArea`），沒有這個問題 |
| **「事件有觸發但沒效果」先 grep 誰還會寫那個欄位** | 先猜機制、再找證據，方向錯了整段都是白工。`grep` 全專案的寫入者是機械性的、不會猜錯 |
| **Windows 版圖形 API 固定 D3D11，不要改回 Auto** | Unity 6 新專案在 Windows 預設 **D3D12**。回饋收集的 exe 在開發機（AMD RX 7900 XTX、驅動 32.0.31041.1004）上**一開就 TDR**：開場題單生完、送出第一張畫面時 `swapchain present failed (887a0005)`、`Device removed reason (887a0006)`＝`DEVICE_HUNG`，事件記錄是 `LKD_0x141_Tdr … amdkmdag.sys … HWS:1`，連三次一模一樣。**改成 D3D11 就不當了**。<br>設定在 Player Settings → Windows → Other Settings：取消 Auto Graphics API，**Direct3D11 放第一**（D3D12 留在第二位當備援）。專案全是 2D sprite 與 UI，用不到 D3D12 的任何功能，而且舊筆電對 D3D11 支援更穩。<br>**根因（D3D12 除錯層查到的）：Unity 6000.3.7f1 的 D3D12 後端在開場上傳貼圖時，把還在排隊的資源提前刪掉**（驗證錯誤 921 ×15、DRED 顯示 78 次 `COPYTEXTUREREGION` 後 page fault），不是驅動無故逾時。<br>另外 6000.3.16f1 才修掉 UUM-137629：某些硬體上**就算沒選 D3D12 也會跑 D3D12 初始化**而當——**新 build 帶到別台電腦之前，要先在那台上完整跑一輪**。症狀：「Editor 正常、exe 一開就驅動逾時」 |
| **有進度存檔之後，改 `initialRating` 不會生效** | 實力從 `PlayerProgress.json` 讀，存檔在就不看起始值——例如為了錄影分段改 `initialRating`，錄出來的起點會是上次玩到的實力，不報錯。開場 log 會說實力從哪裡來；要從頭開始用 **Window → Tangram → 清除進度存檔**（Play 中清沒用，下一局結算會寫回去）。**Windows 上 Editor 跟 exe 是同一個檔**（`persistentDataPath`），在 Editor 玩或清除都會動到這台電腦上 exe 的進度。回饋收集場景**不讀不寫**（`FeedbackSessionController.Awake` 關掉的） |
| **出題器與逼近在背景執行緒跑** | **主執行緒不能直接叫 `generator.Generate`**——要題目走 `LevelController.EnterNextLevel(int)`（經過 `TargetedPrefetch`，它保證同一時間只有一件工作碰出題器）。直接叫的話兩條執行緒同時碰去重表與亂數，症狀是偶爾重複出題或去重壞掉，**不報錯、實機幾乎重現不出來**。丟進 `BackgroundJob` 的工作**只能放純 `Data` 層的計算**：不碰 Unity 物件、不印 log（要印的放進結果，主執行緒拿到再印）。新增會被背景讀的 `Data` 類別時，**用到才建的靜態快取要嘛無害（兩條同時建結果一樣），要嘛加鎖**（`TangramSolver` 的做法） |
| **監控 overlay 在正式 build 要靠 `TANGRADE_MONITOR` 才出現** | 左上角的 `DebugOverlay`（監控面板）只在 Editor、Development Build、或 Scripting Define Symbols 有 `TANGRADE_MONITOR` 時出現。這個條件只寫在 `DemonstrationBuild.IsActive` 一個地方，**同一個開關還管 K 的 10 倍（不是展示版就是 1 倍）、主畫面的「清除紀錄」鈕與「快速提示」勾選**——忘了加符號的話一起不見。**符號一個平台一份，只加 Android**——加在 Windows 的話遊戲版 exe 也會讓玩家看到分數。**展示用的 build 不要勾 Development Build**：面板照樣有，但作弊鈕（`DebugTools`）與浮水印也會跟著出現。忘了加符號的症狀是「展示時看不到面板」，不報錯 |
| **改難度權重之後要跑重算工具** | 權重唯一的源頭是 `Assets/Resources/DifficultyWeights.json`（遊戲從 `Resources` 讀，程式裡沒有預設值），難度的尺度（`mean`／`deviation`）是存下來的常數。**改權重** → 跑 `[Explicit]` 的 `RescaleDifficultyWeights`（重算換算倍率與出題器的目標難度範圍，只寫回有變的數字）→ 範圍變了就重跑生成時間表 → 縮圖牆重新匯出。不跑工具的話尺會被拉長或壓扁，不報錯。夾住範圍（`minimumTargetDifficulty`／`maximumTargetDifficulty`）也住在權重檔，一律走 `DifficultyWeights.TargetRange`，不算進權重指紋。**改出題器的分布或特徵函數**則會讓這個工具失敗（各特徵的平均與標準差對不上）——那代表整把尺要重定。詳見 `程式說明書.md` §13.8 |
| **專案只開了新 Input System** | `ProjectSettings` 的 `activeInputHandler: 1`。`Input.mousePosition`、`Input.GetMouseButton` 這些舊 API 在 runtime 會直接丟例外。輸入一律用 `UnityEngine.InputSystem` 的 `Pointer.current` / `Touchscreen.current` |
| **`transform` 不能存旋轉** | 正方形 `rotation = 0` 與 `= 2` 的 transform **完全相同**，反推不回來。旋轉一定要有自己的 int 欄位，transform 只是輸出。位置反過來可以放 transform（浮點 round-trip 無損），前提是不掛在有旋轉或縮放的父物件下 |
| **模型的翻面是垂直翻，不是水平** | `Symmetry.MirrorAcrossXAxis` 是 (x, y) → (x, −y)。所以 Sprite 要用 `flipY` 不是 `flipX` |
| **兩個 pixels per unit 撞名** | Sprite 匯入設定的 **Pixels Per Unit** = 紋理像素 → 世界單位（固定的資產設定）；`SnapSolver.Settings.ScreenPixelsPerModelUnit` = 模型單位 → 螢幕像素（相機 fit 算出來，**每題都變**）。搞混不會報錯，只會手感很怪 |
