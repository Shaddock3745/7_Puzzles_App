# 七巧板：題目與過程的儲存規格

> 本版取代先前的筆記。所有結論皆已用程式驗證，數據附於文末。

## 0. 全域約定

**單位**：小三角的股 = 2

| 片 | 數量 | 邊長 | 面積 | 節點數 |
|---|---|---|---|---|
| 小三角 | 2 | 股 2、斜邊 2√2 | 2 | 4 |
| 正方形 | 1 | 邊 2 | 4 | 4 |
| 平行四邊形 | 1 | 2 與 2√2 | 4 | 6 |
| 中三角 | 1 | 股 2√2、斜邊 4 | 4 | 7 |
| 大三角 | 2 | 股 4、斜邊 4√2 | 8 | 11 |

總面積 **32**；大正方形邊長 4√2；七片節點總數 **47**。

**座標型別**

```ts
type Scalar = { n: number; m: number };   // n + m√2，n、m 皆整數
type Vec2   = { x: Scalar; y: Scalar };
```

浮點只允許出現在繪圖與拖曳暫態，永不寫回模型。

**節點定義**：頂點 + 邊上細分點，每條邊的合法偏移集合為
`{ 2a + 2b√2 | a, b ∈ ℕ }` 且 ≤ 邊長。

（兩個家族都要。小三角轉 45° 後，長 2 的股會貼在大三角斜邊上，端點落在偏移 2、4 —— 都不是 2√2 的倍數。）

## 1. 過程（拼法 / 解）

### 儲存格式：相對編碼

```ts
type Kind = 'LARGE_TRIANGLE' | 'MEDIUM_TRIANGLE' | 'SMALL_TRIANGLE' | 'SQUARE' | 'PARALLELOGRAM';

type Arrangement = {
  key: string;                                    // canonical hash（見 §1.3）
  puzzleKey: string;                              // 指向 Puzzle
  pieces: { kind: Kind; rotation: 0|1|2|3|4|5|6|7; flipped: boolean }[];   // 7 個
  links:  { firstPiece: number; firstNode: number;
            secondPiece: number; secondNode: number }[];                  // 固定 6 條
  createdAt: string;                              // ISO-8601 UTC
};
```

**不存任何座標。**

### ⚠️ 這一段 2026-09-12 改過：原本寫的格式實作不出來

**這份規格原本寫的是 `LARGE_TRI` / `rot` / `flip`，以及 `links: [pi, nodeA, pj, nodeB][]`。
程式從一開始就沒照著寫，2026-09-12 決定<b>改規格去對程式</b>，理由三個：**

| # | 理由 |
|---|---|
| 1 | ⚠️ **`links` 那個四元組陣列在 Unity 裡序列化不出來**——`JsonUtility` 不支援陣列的陣列。這不是實作偷懶，是那個格式在這個技術棧上不可行。**所以規格無論如何都得改** |
| 2 | 那些縮寫（`rot`、`flip`、`MED_TRI`、`PARA`）**違反專案自己的命名規則**（`文件/開發須知.md`〈命名規則〉：識別字一律用完整單字）。⚠️ 這份規格寫在那條規則訂立**之前**。而**儲存契約是最不該有縮寫的地方**——`MED` 是 medium 還是 median？程式裡看錯有型別擋著，JSON 字串看錯是靜默錯誤 |
| 3 | 程式那份有 round-trip 測試驗過，規格那份從來沒被實作過。改沒驗過的那邊風險低 |

💡 **省下的空間不值得提**：`LARGE_TRIANGLE` 比 `LARGE_TRI` 每片多 5 byte，一題七片 = 35 byte。
一題完整約 1.1 KB，500 題約 550 KB——在 `Resources` 裡是背景雜訊等級。

⚠️ **改的時機是「一題都還沒存」的那一天**。之後每存一題，改動就多一題要轉檔。

### 1.1 為什麼成立

方向已知時剛體只剩 2 個自由度，**一個接觸點就固定住**。所以「每片的 rot/flip」+「生成樹上一條連接」= 完整資訊。

> 對照：方向未知時有 3 個自由度，一個點不夠 —— 這就是純接觸圖失敗的原因（見 §4）。

### 1.2 還原

在 links 上跑 BFS，`t[0] = (0,0)`：

```
t[j] = worldNode(i, a) − transform(protoNode(j, b), rot_j, flip_j)
```

成本 = 6 次向量加減。

**前置條件：links 必須是生成樹（連通）。** 這跟本來就要做的連通性驗證是同一件事，不是額外負擔。

### 1.3 canonical key

相對編碼**不是** canonical form（同一排列有多種生成樹），所以去重一律先還原成絕對座標：

1. 平移到字典序最小頂點為原點
2. 對 16 種整體變換（8 旋轉 × 2 鏡射）各序列化一次
3. 片自身對稱先商掉：三角形的 `flip` 恆設 false；正方形 `rot` 取 mod 2
4. 同種片之間排序（兩大三角、兩小三角）
5. 取字典序最小者 → 雜湊

全程整數，雜湊穩定。

### 1.4 順帶：這個格式就是「組裝過程」

`links` 的 BFS 順序天然是一個合法的擺放順序。若要做步驟回放，把 links 存成**有序陣列**（放置順序）即可，不需要額外的操作紀錄。

## 2. 題目（形狀）

題目重點在形狀，允許多組解 → 與 Arrangement 是 **1:N**。
`puzzleKey` 從七片聯集算出來，不是人工指定。

```ts
type Dir  = 0|1|2|3|4|5|6|7;                    // ×45°
type Edge = { dir: Dir; len: Scalar };
type Walk = { anchor: Vec2; edges: Edge[] };    // anchor 為相對座標

type Puzzle = {
  key: string;
  walks: Walk[];                                 // 外環與洞環都在裡面
  source: 'generated' | 'user_drawn';
};
```

### 2.1 為什麼是「環的集合」

- **點接觸合法** → 邊界會在該頂點經過兩次，不是簡單多邊形
- **允許有洞** → 需要多條環

外環／洞環不存旗標，用 shoelace 有向面積判斷：正 = 外環（CCW），負 = 洞（CW）。

### 2.2 為什麼用邊序列而非頂點清單

- 平移自動消掉，少一個要正規化的維度
- 旋轉 = `dir` 全部加 k mod 8；鏡射 = 反轉序列 + `dir → −dir mod 8`
- 比對兩形狀 = 字串比對

**`anchor` 必須保留** —— 兩條環在哪個點捏在一起，只能靠 anchor + 邊序列還原。

### 2.3 從七片算出 walks

1. 收集所有片的邊，在所有交點處切斷（含 T 型頂點）
2. 保留「兩側材質不同」的邊 → 邊界邊
3. 每條邊界邊定向成「內部在左」
4. 從任一未走過的半邊開始追，追到回起點；重複到走完

**頂點分岔規則**（點接觸靠這條）：

> 以方向 `d` 抵達頂點 `v`，令 `r = d + 4`，從 `r` 開始**順時針**掃描 `v` 的出邊，取第一個找到的。

等價於「取可行的最大左轉」。捏點處會產生兩條各自簡單的環共用一個頂點，而不是一條八字形環。

### 2.4 canonical key

不要對每條環各自正規化再拼回去（anchor 的變換會出錯）。直接重跑：

```
for T in 16 種整體變換:
    把 T 套到 7 個 Placement 上
    重新跑一次 walk 追蹤          // 順便解決鏡射翻轉定向的問題
    平移到「所有環的所有頂點中字典序最小者」為原點
    每條環的邊序列旋轉到自己的字典序最小起點
    walks 依 (anchor, edges) 排序
    序列化
key = min(這 16 個序列)
```

邊數 10～30，重跑 16 次成本可忽略。

## 3. Schema

```
puzzles
  key         TEXT PRIMARY KEY
  walks       JSONB
  source      TEXT

arrangements
  key         TEXT PRIMARY KEY
  puzzle_key  TEXT REFERENCES puzzles(key)   -- 建索引
  pieces      JSONB    -- [{kind, rotation, flipped}] × 7
  links       JSONB    -- [{firstPiece, firstNode, secondPiece, secondNode}] × 6
  created_at  TIMESTAMP
```

- `SELECT count(*) FROM arrangements WHERE puzzle_key = ?` = 這題有幾組解
- Puzzle 可獨立存在（使用者手繪輪廓，還不知有無解）
- 頂點、輪廓、接觸圖、絕對座標 —— **全部不存**，需要時重算

## 4. 為什麼不能只用「節點 + 接觸圖」

已用暴力驗證推翻。兩片的情形就破了：

| 接觸點數 | 圖的數量 | 有歧義的 | 最壞情況 |
|---|---|---|---|
| 1 | 265 | **225** | 一張圖對應 11 種排列 |
| 2 | 232 | 0 | 1 |
| 3 | 19 | 0 | 1 |

**單點接觸是唯一破口，但破得很徹底。** 大三角節點 2 ↔ 小三角節點 2，圖只有一條邊，小三角繞著共用頂點轉 rot=1..6 全部合法、形狀不同、圖一模一樣。

1235 種相異排列中，只有 291 種（23%）能被圖唯一決定。

七片時還多一層：就算每一對片都是邊貼合，兩個各自剛性的**子組件只靠一個點相連**時，整體一樣會鉸鏈式旋轉。

→ 所以必須補上 `rot` / `flip`。補上之後 200/200 往返成功。

## 5. 驗證清單（每次改動後跑）

- **座標封閉**：5 種原型 × 8 旋轉 × 2 翻轉，全部留在 ℤ[√2] 內
- **面積**：所有環有向面積總和 = 32
- **無重疊**：任兩片內部交集面積 = 0（凸多邊形 → SAT + 精確算術）
- **連通**：union-find，共用至少一點即相連（點接觸算數）
- **往返**：encode → decode → 與原排列一致

## 6. 陷阱清單

| 陷阱 | 說明 |
|---|---|
| **翻轉反轉繞向** | flip 後多邊形變順時針，point-in-polygon、shoelace、SAT 全會錯。任何 transform 之後都要重新正規化繞向。 |
| **取樣點判重疊** | 用探針格判覆蓋時，薄片重疊會從格子縫溜過去，跑出「面積正確但有重疊」的假解。探針只能當剪枝啟發，重疊一定要走精確 SAT。 |
| **45° 旋轉不封閉** | `(n+m√2)·√2/2 = m + (n/2)√2`，需要 n 為偶數。原型座標剛好滿足，但 `rot45()` 裡的 assert 要留著。 |
| **共線邊合併** | 只在該頂點邊界度數 = 2 時合併。捏點度數是 4，合併會毀掉拓樸。 |
| **重疊判定要嚴格** | SAT 中距離 0 算「分離」，只有內部交集 > 0 才是重疊。否則所有邊接觸和點接觸都誤判。 |
| **相對編碼非 canonical** | 同一排列有多種生成樹，去重前必須還原成絕對座標。 |

## 附錄 A：解題器 / 出題器

相對編碼在生成端的價值：候選天然只產生「貼合且連通」的擺法，非法狀態根本不會被生成。

實測（填滿邊長 4√2 的正方形）：

1. **候選封閉**：從盤面錨點出發，反覆吸收新擺法的節點直到不再成長 → 2833 個錨點、23916 種合法擺法
2. **bitmask exact cover**：每步強制覆蓋「索引最小的未覆蓋探針」
3. 重疊用精確 SAT，探針只負責剪枝

結果：**0.2 秒找到 3 組解**，面積 32、零重疊、座標全為 ℤ[√2] 整數、往返還原一致。

## 附錄 B：拖曳吸附（互動層，不入庫）

```
1. 候選 = { P − Q }  對所有「已放置片節點 P」×「拖曳片節點 Q」   ← 結果必為精確值
2. 評分 = |toFloat(候選) − 目前浮點位置| 換算成螢幕像素，超過半徑丟掉
3. 排序後逐一驗證重疊，第一個通過的採用
4. 全落空 → 保持自由拖曳
```

七片節點 47 個，拖曳一片的候選上限約 47 × 11 = 517，每幀跑完無壓力。

**關鍵**：候選集合裡全是精確座標 → 模型層根本無法表示「差一點點」的狀態。不是靠容差判定相等，是近似值不存在。

手感細節：吸附半徑用螢幕像素（約 18px）；加遲滯（吸附 18px／脫離 30px）；旋轉軸心用目前吸附的節點；`rot` 天生離散，自由旋轉直接 `round(θ/45°)`；flip 只對平行四邊形開放。
