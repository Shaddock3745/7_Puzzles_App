# 除錯記錄

> 每查到一個「不會報錯但行為不對」的問題就記一則。
> 這個專案的 bug 幾乎都是這種——不當機、不噴訊息，只是「怪怪的」。
> 最後更新：2026-10-20（新增 016 逼近驗收裡的貓都只有軀幹——具象題的外框在捏點斷成好幾個環，驗收工具只取最大的那個；之前的逼近成績全部被低估）
> 前一版：2026-10-17（新增 015 掃描題整隻貓上下顛倒——協作者的 JSON 是 y 朝上；盒子與照片從同一份 JSON 算，所以一起倒、彼此還對得上）
> 前一版：2026-10-14（新增 014 逼近搜尋的 IoU 跑出 1.016——共用邊上的格子被兩片各算一次，而且平移微調會偏好那種位置）
> 前一版：2026-09-24（新增 013 抽屜裡的縮圖有一塊按不到——作弊鈕沒跟著退場，是 D 區技術債真的爆掉；也猜錯一次）
> 前一版：2026-09-15（新增 012 盒子進關時連抖十幾幀——猜錯兩次，量了才知道是回授迴圈）
> 前一版：2026-09-14（新增 011 exe 一開就讓 AMD 驅動逾時——這一則會當機，收進來是因為猜錯的方向特別多）
> 前一版：2026-09-09（新增 004 undo 鈕永遠不出現、005 完成彈窗蓋不住盤面；並更正 003 結尾一段講錯的話）

## 格式

每則四段，缺一不可：

| 段落 | 要寫什麼 |
|---|---|
| **原本預期** | 應該看到什麼 |
| **實際發生** | 真的看到什麼 |
| **原因** | 為什麼會這樣，**以及怎麼發現的** |
| **處理** | 做了什麼。**失敗的嘗試也要寫** |

**「怎麼發現的」與「失敗的嘗試」是這份文件真正的價值。** 結論通常一行就講完了，但下次遇到類似症狀時，能幫上忙的是「當時往哪裡找、哪些方向是死路」。

## 001：盒子畫在離相機很遠的地方（2026-09-04）

**牽涉**：`BoxView`、`LevelController`、`BoardView`
**階段**：P1-3 做完、場景第一次接線

### 原本預期

按 Play 之後，相機自動 fit 到盒子，畫面上出現經典大正方形的容器（灰底 + 白框），位置在畫面上半部。

### 實際發生

- 相機**有動**（`orthographicSize` 與位置都變了）
- 但畫面沒有包住盒子——盒子被畫在相機視野的左上方外面
- Console **完全沒有訊息**：沒有例外、沒有警告

### 原因

**`BoxView` 物件的 Transform 在 `(-8.39687, 0.73846, 0)`，不是原點。**

`BoxView` 的 mesh 是**直接建在世界座標**的（頂點就是模型座標，因為模型:世界 = 1:1、盒子原點是 `Zero`）。Unity 渲染時還是會把 mesh 再乘上物件的 transform，所以整個盒子被平移了 `(-8.4, +0.74)`。

**相機從頭到尾都是對的**——它 fit 的是 `Region.Bounds`，也就是模型認定的位置。被推走的是畫面。

#### 怎麼發現的（這一段是重點）

前四步全部走錯方向，因為**症狀描述錯了**。

一開始的描述是「相機沒有自動對過去」，所以我全部往「`EnterLevel` 沒跑到」的方向查：

| 查了什麼 | 結果 |
|---|---|
| 四支腳本在不在場上（比對 `.meta` 的 GUID 與場景裡的 `m_Script`） | ✅ 都在 |
| 元件是不是孤兒（`GameObject` 的 `m_Component` 有沒有列到它） | ✅ 都有掛上 |
| 物件 active、元件 enabled、`targetCamera` 指對、場上只有一台相機、有 `MainCamera` tag | ✅ 全部正常 |
| 六支有沒有進 `Assembly-CSharp.csproj`（確認 Unity 真的在編它們） | ✅ 都在 |
| Unity 的 `Editor.log` 有沒有例外 | ✅ 一個都沒有 |

到這裡靜態面全部乾淨，我猜是「我的 null 檢查把失敗吞掉了」（見下面的處理二）。

**真正的轉折是一張 Scene 視窗截圖，加上一句修正過的描述：「相機有動但沒包住 BoxView」。**

這句話把問題從「沒執行」變成「執行了但位置不對」，方向整個換掉。接著就能從截圖量出來：

```
盒子邊長 5.66 個模型單位，圖上約 180 px  →  這張 Scene 視窗約 32 px／模型單位
盒子離「它該在的位置」差約 (−261, +24) px  ÷ 32  =  (−8.2, +0.75) 模型單位
場景檔裡 BoxView 的 m_LocalPosition = (−8.39687, 0.73846)
```

數字對上，確認。

**教訓**：症狀描述錯一個字，診斷就會整條走錯。**先確認「什麼東西動了、什麼沒動」再開始找原因**——「相機沒動」與「相機動了但對錯地方」是兩個完全不同的問題。

### 處理

**一、`BoxView` 自己把 transform 拉回 identity（已做）**

原本這個要求只寫在 XML doc 裡：「這個物件的 transform 必須維持 identity」。**寫在註解裡的規定等於沒有保護**——物件被隨手拖過、或從別的物件複製出來，就破了。

改成 `Awake` 裡呼叫 `EnforceIdentityTransform()`：不是 identity 就 `LogWarning` 說明原因，然後改回原點。

**二、`LevelController` 的 null 檢查改成會講話（已做，但這不是本次的原因）**

查的過程中發現的另一個缺陷：

```csharp
if (boardView != null) boardView.SetBox(...);   // 找不到就安靜跳過
```

`boardView` 在 Inspector 沒指，靠 `FindFirstObjectByType` 找。萬一沒找到，這一行什麼都不會說。改成找不到就 `LogError`，另外在 `SetBox` 之後檢查 `Solution.IsValid`，無效就 `LogWarning`。

**這次的 bug 不是它造成的**，但它會讓下一次類似的問題一樣難查，所以順手修掉。

**三、想過但沒採用的**

| 想法 | 為什麼不採用 |
|---|---|
| 把 mesh 改成建在**局部座標**（用 `InverseTransformPoint`） | 有旋轉或縮放時仍然會壞，只是壞得比較隱晦。mesh 本來就該跟模型座標一致 |
| 只 `LogWarning` 不自動修正 | 警告會被滑過去，而症狀（盒子在畫面外）看起來不像 transform 的問題 |

### 還沒處理的同類問題

**`PieceView` 也有一條只寫在註解裡的規定**：「不能掛在有旋轉或縮放的父物件底下」（因為 `transform.position` 的 round-trip 才會無損）。

但它的條件跟 `BoxView` **不一樣，不能照抄**——`PieceView` 只有**旋轉與縮放**會壞，**純平移沒事**（目前 `PiecePreview` 就是純平移的父物件，完全正常）。

**2026-09-04 決定：不加檢查。** 改成之後把七片統一掛在一個**鎖死的父元件**底下。
理由是那樣一個物件就保證七片，比七個各自驗划算；真的出問題再回來處理。
（做那個父元件時，`BoxView.EnforceIdentityTransform` 可以原封不動搬過去。）

## 002：吸附看起來沒對齊——一半是錯覺，一半是真的 bug（2026-09-04）

**牽涉**：`PieceSpriteLibrary`、`BoxView`
**階段**：P1-6 做完、第一次實際拖片

### 原本預期

片吸到盒子角落時，看起來要跟盒子的邊**貼齊**。

### 實際發生

大三角吸到左上角之後，橘色的片跟盒子的邊之間有一條明顯的縫，看起來像沒對準。
**下面的角落看起來比較齊、上面的比較不齊**，正方形則四個角都還好。

### 原因

**吸附完全正確**，用 Scene 視窗看碰撞盒（綠色輪廓）就一目了然：
碰撞盒的頂點跟盒子的角**完全重合**，被往內縮的只有畫出來的橘色。

但縫的成因**不只是視覺**——其中一半是盒子的框線真的佔了內部空間，那是 bug。

縫的寬度是**兩件事加起來**的：

| 來源 | 值（模型單位） |
|---|---|
| `PieceSpriteLibrary` 的 `insetModelUnits` | 0.05 |
| ~~`BoxView` 的 `outlineWidth` 一半~~ | ~~0.04~~ **已修**：框線原本是**置中**畫的，往內吃掉一半。改成**只往外畫**之後這一項歸零 |
| **合計** | 修好之後只剩內縮的 **0.05** |

另外 `cornerRadiusModelUnits = 0.12`，所以**轉角處縮得更多**——這就是為什麼「角落看起來特別不齊」。

至於「上面比下面不齊」：大三角在不同角落用到的是不同的角（直角 vs 銳角），
**銳角被圓角吃掉的面積遠大於直角**，所以同樣的圓角半徑，銳角那端看起來縮得多很多。

#### 怎麼發現的

**我先給了一個錯的解釋。** 在只有文字描述、沒有畫面的情況下，我推測是
「`Candidates` 的距離篩選排在 `isAllowed` 前面 → 合法的候選離手指太遠被篩掉」。
那個機制**確實存在**，但不是這次的原因。

推翻它的是一張 **Scene 視窗的截圖，而且畫面上同時看得到碰撞盒的輪廓**。
綠線跟盒子的角重合 → 吸附是對的 → 問題只可能在畫出來的東西上。

**教訓跟 001 是同一個**：001 是症狀描述錯了，這次是**沒有畫面就先給機制解釋**。
兩次都是「先確認事實，再解釋原因」。
⚠️ 下次遇到「位置看起來不對」的問題，**第一件事是把碰撞盒／輪廓叫出來看**，
那會直接分開「模型算錯」與「畫錯」兩種可能。

### 處理

**一、框線改成只往外畫（已做）——這一項是真的 bug，不是調參**

`BoxView.AppendOutline` 原本把四邊形**置中**在邊界線上（`±halfWidth`），
所以有一半跑到盒子裡面，**佔掉了片本來可以用的空間**。改成只往外畫。

方向可以統一算，不用分外環洞環：`Region` 的外環是 CCW、洞環是 CW，
**所以區域內部永遠在有向邊的左側**——右法線就是「外」。
洞的框線因此畫在洞裡面，一樣不吃可用空間。

**二、內縮與圓角拉到 Inspector（已做）**

`PiecePreview` 多兩個滑桿（`insetModelUnits`、`cornerRadiusModelUnits`），
**Play 模式下拉了會即時重生五張圖**。原本它們是建構式的預設值，
調一次要改程式重編譯——**調參之前得先能調**。

⚠️ 滑桿上限卡在 0.25：侵蝕量是「內縮 + 圓角」相加，而小三角的內切圓半徑只有約
0.586 個模型單位。超過的話 `ErodeConvexPolygon` 會自動對半砍，不會壞但形狀不如預期。

**三、剩下的是純美術，還沒定**

`insetModelUnits`（0.05）與 `cornerRadiusModelUnits`（0.12）的最終值要玩過再定。
`互動設計.md` §13.7 標的就是「P1 先隨便弄」。

**想過但沒做的**：把片的圖改成不內縮、改用真的描邊。那會讓「片與片之間看得出分界」
這個需求回到原點——內縮本來就是為了取代描邊（§13.7），改回去等於推翻那個決定。

## 003：旋轉鈕按了完全沒反應（2026-09-07）

**牽涉**：`PiecePreview`、`TouchInputController`、`PieceActionButtons`
**階段**：P1-8 旋轉／翻面鈕，剛接完線第一次測

### 原本預期

選取一片（高亮），右下角出現旋轉鈕，按一次片轉 45°。

### 實際發生

- 按鈕有出現、有按下的動畫
- 使用者在 `OnRotatePressed` 塞 `Debug.Log`，**事件確實有觸發**
- 高亮**沒有消失**
- **但片一動也不動**
- Console 沒有任何例外或警告

### 原因

`PiecePreview.Update()` 每一幀無條件呼叫 `ApplyInspectorValues()`，那支對七片做：

```
piece.Rotation   = rotation % 循環長度;     ← 從 Inspector 的滑桿
piece.IsFlipped  = flipped && CanFlip(...);
piece.IsSnapped  = showAsSnapped;
```

按鈕改掉旋轉格數之後，**下一幀就被蓋回滑桿上的值**。

`PiecePreview` 是 P1-2 的驗證鷹架，本來只是「排七片給你看形狀」，
但因為 **P1-5 還沒做，它目前是場上唯一會生出七片的東西**——
所以它從「展示用」變成了「每幀重設七片姿態的人」，跟真正的系統搶同一批片。

**怎麼發現的**：走了一段冤枉路。

1. 先看到「事件有觸發但沒作用」，推論是 `ActionTarget` 回 `null`，
   而最可能讓它變 null 的路徑是**按鈕的按下被當成「按在空白處」把選取清掉**
   （`BeginPress` 找不到片就會 `SetSelection(null)`）。
   → **這個推論是錯的**
2. 請使用者看 overlay 的「選取」那一行。**回報「選取沒變」** ——
   一句話就把整條推論砍掉了：選取還在，代表 `ActionTarget` 不是 null
3. 使用者自己提出方向：「是不是你沒有蓋對順序（片的方向是靠 int 強制轉到對應角度）」
4. 照那個方向 `grep` 全專案「誰會寫 `.Rotation =`」，兩個寫入者，
   一個是按鈕、另一個就是 `PiecePreview` 的每幀覆蓋

**教訓（跟 002 同一條，又踩一次）**：
先給機制解釋、再找證據，方向錯了整段都是白工。
**「事件有觸發但沒效果」的第一步應該是「全專案 grep 誰還會寫這個欄位」**，
那是機械性的、不會猜錯，而且這次直接就命中。

### 處理

`ApplyInspectorValues` 改成**只有那三個值真的被拉動才推**
（記住上次推過的值，跟現在比，一樣就直接回去）。
作法跟同一支裡 `RebuildSpritesIfParametersChanged` 偵測滑桿變動的方式一致。

**順帶抓到的第二個 bug**：`piece.IsSnapped = showAsSnapped` 也是每幀強寫，
等於在跟 `TouchInputController` 搶。拖曳之所以看起來一直正常，
**只是因為 `TouchInputController.Update` 剛好排在 `PiecePreview` 後面**，
而 `MonoBehaviour` 之間的 Update 順序是**未定義**的——
換台機器、改個腳本執行順序就可能翻過來。同一個修法一起解掉。

**失敗的嘗試**：把 `pressBlockingAreas` 從「Inspector 手動填」改成
「`PieceActionButtons` 自己註冊」。**對這個症狀完全沒用**，因為根本不是那個原因。
不過那個改動本身留著——「要記得填一個陣列，功能才會動」本來就是這專案要消滅的模式，
而且漏填的症狀（按鈕沒反應）跟這則長得一模一樣，之後會很難分辨。
同時在 `RotateSelected` / `FlipSelected` 加了「沒有作用對象就印警告」，
把那條原本安靜的路變吵。

**✅ 已於 2026-09-08 做掉**（P1-5）：`PiecePreview` **整個刪掉了**。
它已經不只是沒用，是會主動製造這類問題——它持有七片，卻不知道有別人也在動那七片。

⚠️ **2026-09-09 更正**：上面這段原本寫「`TrayView` 只寫 `IsVisible`，而控制器不寫這個欄位，
兩邊的欄位集合完全不重疊」——**那是錯的**。控制器也寫 `IsVisible`
（`SummonFromTray`、`RecycleDrag`，以及 P1-9 的 undo 與清空收尾）。

**真正的差別是真相在哪**，不是誰寫哪個欄位：

| | 真相 | 每幀寫的那一份是什麼 |
|---|---|---|
| `PiecePreview` | **它自己**（Inspector 滑桿） | 第二個真相，會跟控制器搶 |
| `TrayView` | `LevelData.IsInTray` | **投影**。控制器是在改完 `LevelData` 的同一刻順手同步一次（為了不閃一幀），所以兩邊永遠一致 |

**這一則留下來的通則**（修正後）：新增任何會碰 `PieceView` 的東西時先問——
**這個欄位的真相在哪？我是在改真相，還是在畫真相？**
兩個地方寫同一個欄位不必然是坑，**兩個地方各自認定真相才是**。

## 004：undo 鈕永遠不出現（2026-09-09）

**牽涉**：`BoardActionButtons`（當時叫 `UndoButton`）

### 原本預期

放一片進盒子之後 undo 鈕出現，退到沒得退時消失。

### 實際發生

**按鈕從頭到尾沒出現過。** 放幾片進盒子都一樣，Console 完全乾淨，沒有任何錯誤或警告。

而且 undo 的功能本身是好的——把顯示條件的算式單獨拿出來看，每一項都算得出正確答案。

### 原因

**腳本掛在它自己要開關的那顆按鈕上**，而且 `undoButton` 欄位指向自己。

隱藏是 `SetActive(false)` 做的，而 **Unity 停用的物件不會再跑 `Update`**。
所以：

```
一關開始，堆疊是空的
  → 第一幀 Update 算出「不該顯示」
  → SetActive(false) 關掉自己所在的物件
  → Update 從此不再執行
  → 沒有任何機會把自己開回來
```

**它在第一幀就把自己鎖死了**，後面發生什麼都無所謂。

**怎麼發現的**：先把顯示條件那條鏈從尾巴往回推一遍（`Update` → `CanUndo` →
堆疊非空 → 推入點在 `CommitDrag`），每一環都對。既然算式沒錯，
問題就只可能在「算式根本沒被執行」——這時候去翻場景檔，才看到
`undoButton: {fileID: ...}` 指的就是掛著腳本的那顆物件自己。

⚠️ **場景檔是純文字，用讀的比在 Inspector 裡點快**，而且看得到「這兩個 id 是同一個」。

### 處理

場景：把腳本移到獨立的物件上（`PieceActionButtons` 本來就是這樣做的，
只是我寫 `UndoButton` 的場景說明時**漏了寫這一條**）。

程式：`Awake` 加一道檢查，發現「要開關的按鈕就是自己」就印錯誤，
把這條原本安靜的路變吵。同一份說明也寫進 XML doc。

**為什麼不改成「只關掉圖片」就好**：`IsOverBlockingArea` 是靠 `activeInHierarchy`
決定要不要跳過的。只關渲染的話，看不見的按鈕**還是會擋住點擊**，
那塊就變成點不到片的死角——換一個更難查的症狀而已。

**同一天順帶發現的近親**：抽屜開著時，那幾顆按鈕的矩形落在抽屜範圍裡，
而且判定順序排在抽屜前面 → **抽屜裡有幾片點不動**。
修法是同一件事的反面：讓按鈕在抽屜開著時隱藏，隱藏就不擋。

**這一則留下來的通則**：⚠️ **一個 `MonoBehaviour` 不可以停用自己所在的物件**——
它會連自己的 `Update` 一起關掉，而且完全不報錯。
要開關某個東西的邏輯，必須住在**不會被它自己關掉**的地方。

## 005：完成彈窗蓋不住盤面（2026-09-09）

**牽涉**：`LevelCompletePanel`、Canvas 的排序設定、`TrayView`、`PieceView`、`BoxView`

### 原本預期

過關之後彈窗蓋在最上層，玩家只看得到彈窗。

### 實際發生

彈窗**有跳出來、兩顆按鈕也按得動**，但**盤面上的片畫在它上面**——
片穿過彈窗露出來，看起來像彈窗是半透明的。Console 乾淨，沒有錯誤。

⚠️ 而且**同樣的缺陷一直都在**：四顆按鈕也一樣會被片蓋住，
只是它們在畫面角落、那裡剛好沒有片，所以一個多禮拜都沒被發現。

### 原因

**所有 renderer 都在 `Default` 這一個 sorting layer 裡，先後全靠各自挑的數字。**

| | 當時的 sortingOrder | 怎麼來的 |
|---|---|---|
| 盒子 `BoxView` | −1 | 「要比片小」 |
| 七片 `PieceView` | 0 ～ 226 | `PieceSorting` 算的 |
| 抽屜／箭頭／回收框 `TrayView` | **2000 ～ 2002** | 「挑一個夠大的，蓋得過片就好」 |
| Canvas（四顆鈕 + 彈窗） | **0** | Unity 預設值，從來沒人動過 |

同一個 sorting layer 裡先比 order，order 相同才比距離。
Canvas 是 Screen Space - Camera、`PlaneDistance` 100，而片在相機前約 10——
**order 都是 0，於是比距離，片比較近所以蓋在上面。**

**怎麼發現的**：`grep` 場景檔的 `m_SortingOrder` 與 `m_RenderMode`，
再對照三支程式裡寫死的 order 常數。四個數字放在一起就看得出問題了。

### 處理

⚠️ **第一個想到的修法是錯的方向**：把 Canvas 的 sorting order 調成 3000。
那**會動**，五秒改完。使用者否決了，理由是「**我們應該改分層而不是一直調 order 的數字**」。

那句話點破的是：這些數字之間沒有任何機制保證關係成立，
**那不是排序，是巧合**——哪天有人把抽屜調到 4000，同樣的症狀會再來一次。

改成 **sorting layer**（`Box → Piece → GameUI → CompleteUI`）：
跨系統的先後由 `TagManager.asset` 一個地方決定，各系統的 order 只在自己那層裡有意義。
抽屜那三個數字從 2000/2001/2002 縮回 0/1/2。

**失敗的嘗試（使用者先試過的）**：

| 試法 | 結果 |
|---|---|
| 調 z 座標 | 沒用。**透明佇列裡 sorting layer / order 優先於距離**，z 只在 order 打平時才有話語權 |
| 只關掉 `BoxView` | 沒用，而且方向錯了——盒子是 −1，本來就在 Canvas **下面**。蓋住彈窗的是片與抽屜 |

**這一則留下來的通則**：⚠️ **能動的修法與對的修法可能差一整個結構。**
「調一個數字就好了」的時候先問一句：**這個數字為什麼是對的，有什麼東西會在它變錯時告訴我？**
沒有答案的話，那就是一個等著再爆一次的巧合。

## 006：盒子外框在生成的題目上長出刺與缺口（2026-09-10）

**牽涉**：`BoxView.AppendOutline`、`Region.Rings`、P2-4 第一次看到生成的題目

### 原本預期

盒子的白色外框沿著輪廓走一圈，粗細一致，轉角乾淨。

### 實際發生

換成演算法生成的題目之後，外框在轉角處出問題——**有些角露出缺口，有些角長出一根刺**。
而**刺是往盒子內部戳的**，不是往外。

⚠️ 這個缺陷**從 P1-3 就一直存在**，但經典大正方形上完全看不出來，
所以一個禮拜的實機測試都沒發現。

### 原因

當時的畫法是：每條邊鋪一個往外偏移一個線寬的四邊形，
**兩端各多伸出「一個線寬」**，讓相鄰兩條在轉角處重疊。

⚠️ **「一個線寬」這個長度只在 90° 轉角剛好正確。**
兩條垂直的帶子各伸一個線寬，剛好補滿角落那個 w×w 的正方形——
不多不少，看起來完美。

其他角度全錯：

| 轉角 | 會怎樣 |
|---|---|
| **90°** | 剛好補滿 ✅ |
| **45°（銳角）** | 要補的楔形大得多 → 伸不夠 → **缺口** |
| **135°（凹角）** | 兩條帶子本來就重疊 → 還往外伸 → **刺** |

**怎麼發現的**：P2-4 把生成的題目塞進遊戲玩，第一眼就看到外框怪怪的。
⚠️ **經典大正方形四個角全是 90°**，所以它是唯一一個會讓這個 bug 完全隱形的形狀——
而它正好就是 P1 全程唯一的那一題。生成題的凹角中位數是 8，一撞就現形。

💡 **這一則跟 005 是同一個病**：一個「剛好對」的數字，
沒有任何東西在它變錯時會告訴你。005 是 sortingOrder 挑「一個夠大的數字」，
這裡是延長「一個線寬」。兩個都在唯一被測過的那個情境下剛好成立。

### 處理

⚠️ **修了兩次，第一次的修法也是錯的**，這一段是重點。

**第一次修（錯的）**：邊不延長，改成「只在**凸角**補一個三角形」。
理由是「凹角那裡兩條帶子本來就重疊，不用補」。

**那個理由只在鈍的凹角成立。** 凹角很銳的時候（notch 很窄），
帶子的角落是從頂點**垂直**推出去的，而那個垂直方向會**跨過另一條邊、戳進材料裡**。
所以刺沒有消失，只是換了個成因——而且症狀一模一樣。

⚠️ **是使用者實測回報「往內的銳角還是會有凸出去」才抓到的**，
不是自己推出來的。改對了一半的東西看起來很像改好了。

**第二次修（對的）**：**相鄰兩條帶子共用同一個 miter 點**（兩條偏移線的交點），
一條邊一個四邊形，不另外補角。

| 角的種類 | miter 點落在哪 | 效果 |
|---|---|---|
| 凸角 | 外面 | 自動把楔形缺口**補滿** |
| 凹角 | 比垂直推出去更靠內 | 自動把帶子**裁短**，戳不出去 |

**同一條式子涵蓋兩種情況**，所以連「哪些角要補」都不必判斷。
公式是 `(n₁ + n₂) · w / (1 + n₁·n₂)`，長度等於 `w / cos(半夾角)`。

兩個有界性都查過並寫進註解：45° 網格上 miter 最長是 135° 轉角的 **2.6 倍線寬**；
邊長（最短 2）比線寬（0.08）大 25 倍，偏移環不會自我相交。
⚠️ **（2026-09-11 更正）「邊長最短 2」是錯的**，那是片的原型邊長；輪廓切斷之後最短只有 0.343。
而且這一則只考慮了一般頂點，**捏點上的描邊會畫進材料裡**——見 010。
接近原地折返時分母趨近 0，有 fallback。

**這一則留下來的通則**：

⚠️ **只有一個測試情境的時候，「看起來對」不等於「對」。**
P1 全程只有一題，而那一題偏偏是所有角都 90° 的正方形——
它同時隱藏了這個 bug 與 005 那個。**測試資料的多樣性本身就是覆蓋率。**

⚠️ **改對一半比沒改更難發現。** 第一次修之後刺還在，但成因換了；
如果當時沒有實機再看一次，會以為「還沒修好」而不是「修錯方向」。
幾何的東西**眼睛看不出差別的地方，就用一個極端案例逼它現形**——
這裡是銳角 notch，而生成器剛好會自己產生。

## 007：三角形的洞讓 `Region` 直接丟例外（2026-09-10）

**牽涉**：`Region.FindDoubledInteriorPoint`（現已改名 `FindScaledInteriorPoint`）、P2-5 放寬審美門檻

### 原本預期

把生成的題目載進遊戲，`Region.FromPuzzle` 建得起來。

### 實際發生

```
InvalidOperationException: Region：第 1 條環（洞）找不到內部點。環是退化的，或頂點順序有問題。
```

一按「下一關」就炸。⚠️ **有洞的題目才會，而且不是每一題。**

### 原因

`Region` 對每個洞要存一個「嚴格在洞內部」的點（`ContainsPolygon` 第 4 條規則要用它擋，2026-09-11 起那條改編為規則 6，見 009
「片整個蓋住一個洞」）。舊做法是**試任兩個頂點的中點**，驗它在不在環內，不中就換下一對。

⚠️ **三角形沒有對角線。** 任兩個頂點就是一條邊，中點必然落在**邊界上**，
`Classify` 回 `Boundary` 而不是 `Inside`——所以**每一個三角形的洞都必然失敗**。

它的 XML doc 引了耳朵定理說「保證至少有兩個會中」，**但那條定理要 n ≥ 4 才有對角線可用**。

**怎麼發現的**：P2-5 為了肉眼看「被審美門檻篩掉的形狀能不能用」，
把門檻放寬成洞 ≤ 1，第一次玩到有洞的題目就炸。

⚠️ **而且這個 bug 在預設門檻（洞 ≤ 0）下也會發作**，因為 008 那則會讓洞偷渡進來。
實測預設門檻下 2000 題有 **3 題**（0.15%）一載入就丟例外——一場 20 關大約 3% 會中。

**用實測釘死範圍**（85 條真實洞環）：

| 洞環頂點數 | 條數 | 舊規則成功 |
|---|---|---|
| **3** | 46 | **0** |
| 4 | 37 | 37 |
| 5 / 6 | 2 | 2 |

手工造的對照組也一致：正方形的洞沒事，三角形的洞當場丟同一個例外。

### 處理

改成**「兩條相鄰邊的中點，再取中點」**：連續三頂點 a、b、c → `(a + 2b + c) / 4`。

**為什麼一定找得到**：耳朵定理保證任何簡單多邊形都有耳朵（n = 3 時整個三角形自己就是）。
在耳朵尖 b 上三角形 abc 整個落在多邊形裡，而那個點是三角形**中位線的中點**，
只要 a、b、c 不共線就嚴格落在內部。掃過每一個 b 必然中。

⚠️ **共線的三元組會產生落在邊界上的退化候選**，所以每個候選都要驗過。
這不是理論顧慮——`BoundaryTracer` 的共線邊只在邊界度數 = 2 時合併，
捏點附近真的會留下共線中繼頂點。測試 `洞環有共線中繼頂點時仍然建得起來` 釘住這條。

**代價**：`(a + 2b + c) / 4` 在 ℤ[√2] 裡不可約分，所以 `Region` 內部的放大座標
**從 ×2 變成 ×4**，收進具名常數 `Region.ScaledCoordinateMultiplier`。

⚠️ **不能只把洞的內部點改成 ×4、其餘留在 ×2**——那會讓同一個類別裡有三套座標系，
正是「`Region` 內部有兩套座標系，混用會差一個 2 倍而且不報錯」那個坑的加強版。
所以整套改，連帶：

- `doubledRings` → `scaledRings`、`ClassifyDoubled` → `ClassifyScaled`
- `ContainsPolygon` 第 4 條（現在的規則 6）的 `, 2)` 改成 `, ScaledCoordinateMultiplier)`
- **新增 `ClassifyMidpointOf(a, b)`**——原本有三個地方手寫 `edgeStart + edgeEnd` 組 ×2 中點，
  倍數一改全都要跟著改，而**忘記改不會報錯，只會安靜地判錯**。包成方法之後倍數只出現在一個地方

**失敗的嘗試**：一開始想用**三角形重心** `(a+b+c)/3`。做得出來（把世界乘 3），
但倍數要同時容納中點的 `/2`，會被逼到 **×6**；而且重心**只對三角形有效**，
n ≥ 4 還要另一條規則 → 兩套規則兩個特例。`(a+2b+c)/4` 不分 n 一律通用，倍數只要 4。

**這一則留下來的通則**：⚠️ **引用定理時要連前提一起抄。**
註解寫「耳朵定理保證至少有兩個會中」——定理是對的，但它的前提是 n ≥ 4，
而那個前提沒被寫下來，所以也沒有人去檢查 n = 3 的情況。

## 008：同一個形狀，洞數與凹角會隨姿態和片的順序改變（2026-09-10）

**牽涉**：`BoundaryTracer.Trace` / `NextBoundaryEdge`、`DifficultyFeatures`、`Canonical`、ELO 的地基

### 原本預期

一個形狀的特徵（凹角、洞數、捏點……）**只由形狀決定**。
`DifficultyFeatures` 的 XML doc 把這件事寫成硬需求，理由是
**ELO 要求同一題永遠得到同一個難度值**，而 `Canonical` 把互為旋轉／鏡射的題目當成同一題。

### 實際發生

**不報錯，什麼都不報。** 但：

- 生成器回報「洞 = 0、凹角 = 9」，同一題**存進 `Puzzle.Walks` 之後重量卻是「洞 = 1、凹角 = 11」**
- 500 題裡有 3 題（0.6%）對不起來
- 連帶：**「洞 ≤ 0」這條審美門檻擋不住洞**——生成器拿去比門檻的是前面那一份，
  存進去的是後面那一份。實測預設門檻下 2000 題有 **6 題**偷渡了洞進來，
  其中 3 題因為 007 那個 bug 一載入就丟例外

### 原因

`BoundaryTracer` 沿著邊界走，規則是「材料永遠在左手邊」。
一般轉角只有一條路可走，但**捏點**（兩塊材料只靠一個點相連）度數是 4，站上去要選。

問題出在收工條件：

```csharp
if (arrivalVertex == boundaryEdges[startEdgeIndex].Start) break;   // 舊
```

「走回起點那個**頂點**就收工」。⚠️ **但自我接觸的環會經過捏點兩次**，
所以起點如果剛好是捏點，**第一次經過就被誤判成走完了**，一條環被切成兩條。

而「這一圈從哪條邊起步」是 `for (startEdgeIndex = 0; ...)`——
**索引最小的未使用邊，也就是第一片的第一條邊**，取決於片被列出來的順序。

第二個漏洞在 `NextBoundaryEdge`：候選出邊多一個「**還沒走過**」的條件
（註解自己寫「取**可行的**最大左轉」）。一般頂點無所謂（只有一條出邊），
但捏點有三條候選，**先追的那一圈會先吃掉一條**，後追的只能挑剩下的。

**怎麼發現的**：三步，每一步都是量出來的，不是猜的。

1. P2-5 比對「生成時回報的特徵」與「從 `Puzzle.Walks` 重量的特徵」→ 500 題有 3 題不一致
2. 把那些形狀套 **16 種整體變換**各重描一次 → **洞 = 0 有 8 種姿態、洞 = 1 有 8 種姿態**。
   8 對 8 剛好是鏡射的分界，看起來像是「最大左轉」對鏡射不穩
3. ⚠️ **但再往下查就翻案了**：同一個手性、只把七片**洗牌 200 次** → 環數在 `{1, 2}` 之間跳。
   **所以根因是走訪順序依賴，鏡射只是改變順序的其中一種方式**

### 處理

**轉彎規則不動**——「最大左轉」本身給的就是拓樸上正確的答案：
材料內部有幾塊連通區域就描出幾條環。兩片只靠一角相碰時內部是兩塊 → 兩條環；
挖掉的三角形尖端頂到外框時內部仍是一塊（可以從三角形上面繞過去）→ 一條自我接觸的環。

⚠️ **這個選擇隔天咬人了，見 009。** 被捏點圍住的空地因此**永遠**是外環的一部分，
而 `ContainsPolygon` 當時擋「片蓋住空地」的規則只認得洞環——修 008 之前某些姿態還會被描成洞環、擋得住，
修完之後永遠擋不住。而且討論 008 時建議的其實是「拆成兩圈」（理由正是洞的規則現成），
實作卻保留了一圈、沒有說明換了。

只改兩處：

| | 舊 | 新 |
|---|---|---|
| 出邊的挑選 | 最大左轉，**只考慮還沒走過的** | 最大左轉，**只看角度** |
| 收工條件 | 走回起點那個**頂點** | **下一條就是起點那條邊** |

改完之後「從這條進來、往哪條出去」是頂點上進邊與出邊的**固定一對一配對**，
而配對的循環就是環——**從循環上哪一條邊起步都得到同一個循環**。

💡 順手加了一道防線：配對算出來的下一條如果**已經走過**，直接丟例外。
配對是排列，正常不可能發生；真的撞到代表邊的切分有問題，與其無限繞圈不如當場炸掉。

**驗證**（修前 → 修後）：

| | 修前 | 修後 |
|---|---|---|
| 生成時特徵 vs 存檔後重量 | 3 / 500 不一致 | **0 / 500** |
| 預設門檻下 `Region` 丟例外 | 3 / 2000 | **0 / 2000** |
| 預設門檻下偷渡進來的洞 | 6 / 2000 | **0 / 2000** |
| 十六種姿態下特徵不唯一 | 有 | **0 / 300** |

### ⚠️ 這一則真正的教訓在測試上：第一版的回歸測試是假的

寫了三條測試（`捏點_洞頂到外框時描出一條自我接觸的環`、`捏點_環的組成不受片的枚舉順序影響`、
`捏點_環的組成對十六種整體變換一致`），**全綠**。
把舊的收工條件放回去做變異測試——**還是全綠。**

**原因**：追環從索引最小的邊起步 = **第一片的第 0 個頂點**。
而正方形原型的第 0 個頂點是左下角、`rotation = 0` 時就等於 `Translation`。
第一版 fixture 裡捏點是相鄰兩片的**右下角與左上角**，
**不是任何一片的第 0 個頂點** → 「從捏點起步」那條路徑永遠走不到 → 三條測試全在驗空氣。

⚠️ **洗牌測試也一起瞎掉**：洗牌換的是「哪一片排第一」，但不管哪一片排第一，
索引 0 都是**它自己的左下角**，換來換去都不是捏點。

⚠️ **而且行覆蓋率是滿的**——那個 `break` 判斷式有執行，只是條件從來沒為真。看報告看不出來。

**改法**：把其中一片改成 `new Placement(PieceKind.Square, 2, false, new ExactVector2(4, 4))`
（旋轉 90° 擺在捏點）。**佔的位置跟 `SquareAt(2, 4)` 完全一樣**，
差別只在頂點從哪個角開始數——現在第 0 個頂點就是捏點。再跑變異：**三條全紅**。

💡 **這跟 P2-2 補「不對稱 L 形」是同一類**：

| | 遮住路徑的東西 | 沒補的話什麼寫錯也會過 |
|---|---|---|
| P2-2 | 正方形對 16 種變換幾何上完全相同 | 鏡射整段寫錯 |
| 這次 | 捏點不在任何一片的第 0 個頂點上 | 起點的判斷寫錯 |

**通則**：寫完測試不要問「它綠了嗎」，要問 **「哪一行寫錯它會紅」**。答不出來就代表還沒驗到東西。

⚠️ fixture 那一片為什麼要用旋轉的方式擺，理由寫進註解了——
下次有人覺得「`SquareAt(2, 4)` 比較好讀」順手一改，測試就變回裝飾品，而且照樣全綠。

## 009：被捏點圍住的空地，片可以放進去（2026-09-11）

**牽涉**：`Region.ContainsPolygon`、008 的追邊修法、過關判定 `AllOnBoard` 的前提

### 原本預期

片只能放在盒子裡（碰到邊框也算）。盒子模式的過關判定之所以能退化成 `AllOnBoard`，
靠的就是這條硬限制：七片都合法放好 ⇒ 盒子必然填滿。

### 實際發生

**不報錯。** 使用者實機那一題（種子 20260910 第 318 次呼叫）有一個**被捏點圍住的空三角形**，
兩股都是 2——剛好是小三角的大小。

```
小三角放進那個空三角形 → ContainsPolygon = True
空三角形重心的 Classify   = Outside     ← 區域自己知道那裡是外面
```

片會被當成合法擺放，也就可能被吸到盒子外面；「七片都放好 = 盒子填滿」也可能跟著破。
（這兩個後果只在模型層驗過，沒有在 Unity 裡實際試。）

**範圍**：預設門檻一千題，**79 題**有被捏點圍住的空地，其中 **70 題**的空地本身會被判成合法。
真的放得進一片的上限約 4%（空地面積 ×2 = 4 的有 38 個、= 8 的有 4 個；形狀是否吻合沒有逐一驗）。

### 原因

當時的五條規則**只看片的角和邊，從來不看片的內部**：

| 規則 | 為什麼沒擋下來 |
|---|---|
| 1 頂點都在區域內 | 三個頂點都在邊框上 → 過 |
| 2 沒有真交叉 | 片的邊就貼著輪廓走 → 過 |
| 3 沒有輪廓頂點嚴格在片內 | 沒有 → 過 |
| 4 沒有**洞**的內部點在片內 | **捏點圍住的空地不是洞，沒有內部點可問** → 過 |
| 5 片邊的區間中點都在區域內 | 中點都落在邊框上 → 過 |

唯一會看內部的是當時的規則 4，而它只認得**洞環**。這塊空地是外環的一部分。

⚠️ **008 讓它從「偶爾」變成「必然」**：修 008 之前，這種形狀在某些姿態或片的順序下
會被描成「外環 + 洞環」，那時規則 4 擋得住；修完之後永遠是一條自我接觸的環（見 008 補的那段）。

**怎麼發現的**：使用者問「那張截圖在邏輯層被定義成捏點還是洞」。
重現後確認是捏點（環數 1、捏點在環上出現兩次），接著注意到空三角形兩股是 2 = 小三角，
才去問 `ContainsPolygon`。也就是說，**不是測試抓到的，是追問定義時順手撞到的**。

### 處理

加一條規則，排在規則 3 之後；原本的規則 4 移到最後改名規則 6（只加不刪）：

> **規則 4：沒有任何一段輪廓把區域外側朝向片的內部。**

每條輪廓邊都是「內部在左」，所以右側就是區域外面。每條輪廓邊在「片的頂點落在它中段的地方」切開，
每一小段取中點：嚴格在片內 → 橫過片的內部，違反；落在片的邊上 → 貼著那條邊走，
看片的內部在它哪一側（同向／反向配上片的繞向），在右側就違反；在片外 → 不管。

**為什麼完整**：片的內部如果有一點在外面，要嘛有輪廓碰到片的內部（第一種情況抓到），
要嘛沒有——那片的內部整塊在外，片的邊不是有一段沒貼輪廓（規則 5 抓到），
就是整條貼著輪廓、外側朝內（第二種情況抓到）。完整論證在 `AnyBoundaryFacesOutsideInto` 的 XML doc。

**驗證**：

| | 結果 |
|---|---|
| 使用者那一題 | 小三角放進空三角形 → **False**（兩種繞向都是） |
| 一千題裡被捏點圍住的空地被判成合法 | 70 → **0** |
| 一千題的參考解 7000 片 | **0 片被誤擋** |
| 效能（同一套量法前後比） | 經典大正方形 2.43 → 2.49 µs、17 條邊的生成題 1.15 → 2.11 µs |

**變異測試**（每個變異各跑一份獨立的測試專案）：

| 變異 | 結果 |
|---|---|
| 拿掉規則 4 | 只有 `被捏點圍住的空地_放進剛好一樣大的片_不合法` 紅 ✅ |
| 規則 4 的方向判斷寫反 | 十幾條紅，連 `經典大正方形_七片都判定在盒內` 都紅 ✅ |
| 拿掉規則 6 | 全綠——跟「規則 6 已經多餘」的論證一致 |
| 拿掉規則 5 | ⚠️ **第一次跑全綠** |

最後那一列是新發現：原本守規則 5 的 `跨過捏點的片_不合法`，現在會先被規則 4 擋下，
**整個測試集沒有任何一條在守規則 5**——但規則 5 並不多餘（片整個在凹口裡、只有頂點碰到邊框時，
只有它擋得住）。補了 `只在頂點碰到邊框_整片在凹口裡_不合法`，再跑一次變異：只有它紅。

### 失敗的嘗試

一開始提議的是「**把舊規則 4 換成：片的一個內部點必須在區域內**」，理由是
「規則 1、2、3、5 都過了之後，輪廓不會進到片的內部，所以片的內部整塊在裡面或整塊在外面，問一個點就知道」。

⚠️ **那句理由是錯的，而且是在寫程式之前驗出來的。** 反例：洞的形狀是大三角三邊中點連成的小三角，
上面蓋一片大三角。洞的三條邊兩端都停在大三角的邊上——端點接觸不算真交叉，規則 2 抓不到——
但它們**橫過片的內部**，把它切成裡外兩部分。用 (a+2b+c)/4 取的三個候選點：

```
(1,1) → OnBoundary     (2,1) → OnBoundary     (1,2) → OnBoundary
```

全落在洞的邊上，照那個簡化會放行。現行程式靠當時的規則 4 擋得住，換掉就壞。
`中點三角形的洞被大三角蓋住_不合法` 釘住這件事，防止之後有人做同樣的「簡化」。

**這一則留下來的通則**：

⚠️ **只看邊界的檢查，碰到「邊界全部重合」的情況是瞎的。** 片的邊全貼著輪廓時，
所有取樣點都落在邊框上，每一條規則都說「沒問題」。需要一條會看內部的規則——
而且**不能只看一個點**，因為輪廓可以只靠端點接觸就橫過內部。

⚠️ **改一個模組的輸出形狀，要去查所有消費它的地方的假設。** 008 讓追邊的輸出變成對的，
但 `Region` 的規則當初是假設「被圍住的空地一定是洞環」寫的。兩個模組各自正確，組起來出事，
而且沒有任何東西會報錯。

## 010：捏點上的外框往材料裡戳刺（2026-09-11）

**牽涉**：`BoxView.AppendOutline` / `MiterOffset`、`BoxView.Redraw` 的繪製順序、006 的 miter 修法

### 原本預期

外框只畫在材料外面（002 的設計），而 006 改成共用 miter 點之後，轉角都是乾淨的。

### 實際發生

**不報錯。** 有捏點的題目，捏點那裡會有一根亮色的刺**戳進材料裡面**。
使用者實機截圖那一題：種子 20260910，第 318 次呼叫（審視鷹架，凹角上下限都是 3）。

### 原因

用 `BoxView` 一模一樣的算式在 CPU 上重畫，逐點量「在材料內部、卻被描邊蓋到」的地方：

| | 原因 | 證據 |
|---|---|---|
| **A** 主因 | **捏點上，空楔形的兩條邊在環上不相鄰。** 每個頂點只把「環上前後相鄰的兩條邊」用 miter 接起來，但圍住同一個空楔形的兩條邊分屬捏點的兩次經過，沒有人負責在楔形的尖端把兩條帶子裁齊，帶子就衝過尖端進到對面的材料 | 預設門檻 300 題裡**有捏點的 21 題全中**，最深 2.58 倍線寬。使用者那一題：#0（135° 轉角，材料只剩 45°）的 miter 點 (0.748, 5.464) 落在材料裡，深 2.41 倍線寬。**把 miter 拿掉、只畫純帶子，還是會戳進去**（深 0.63 倍線寬）→ 不只是 miter 太長 |
| **B** 放大 | **45° 材料尖角的 miter 伸到 2.6 倍線寬**，附近有別段材料時尖端就伸過去 | 一般頂點只有 1 / 300 題：尖角旁 0.34 處有另一段材料，被蓋到 0.18 倍線寬深 |
| **C** 看得見 | 描邊畫在填色**之後**，所以任何越界都蓋在灰色上 | `Redraw` 原本的兩行順序 |

💡 **A 跟 008 是同一種病**：在捏點上，**「環上相鄰」不等於「幾何上相鄰」**。
008 在追邊裡犯過一次（用環的順序決定走哪條），這裡在描邊又犯了一次（用環的順序決定接哪條）。
006 修 miter 時只想了一般頂點。

**怎麼發現的**：P2-5 的審視鷹架開始出有捏點的形狀，使用者在實機上看到。
一開始以為跟 007／008 有關，修完那兩個之後刺還在——因為那兩個都在模型層，畫面層一行沒動。

### 處理

**對調繪製順序：先描邊、後填色。** 填色 = 七片的聯集 = 材料本身；
描邊照設計只該在材料外面，所以填色蓋掉的只有越界的部分，該留的描邊一點都不會少。
兩個顏色的 alpha 都是 1，是整個蓋掉而不是混色。

⚠️ **這是遮，不是修。** 越界的幾何還在，只是被蓋住：填色改成半透明、或 `referenceSolution` 傳 null
（`Redraw` 允許，那時只畫輪廓）時，刺會跑回來。沒做的兩個：

| 做法 | 解掉什麼 | 為什麼先不做 |
|---|---|---|
| 接角改用幾何上相鄰的邊（每個頂點把邊依角度排，每個空楔形用自己的兩條邊接） | A 從根上解掉 | 要改 `AppendOutline` 的結構，而現在遮起來已經看不到了 |
| miter 加長度上限 | B；A 只能縮短 | 同上；但**想把線調粗之前一定要做**（見下面 D） |

✅ **2026-09-11 使用者在 Unity 裡看過，效果可以接受。**（`BoxView` 不在 `dotnet` 測試專案裡，這一步只能靠實機。）

### 失敗的嘗試與被推翻的推測

| 推測 | 怎麼被推翻的 |
|---|---|
| 捏點上兩次經過之間有**沒畫到的缺口** | 1401 個取樣點，0 個沒被蓋到。方向相反：是畫太多，不是畫太少 |
| **一般頂點也普遍會戳進去（3.27%）** | ⚠️ **那是量測工具自己的誤差，而且被寫進了待辦清單**：判斷「在不在材料裡」時把取樣點量化到 1/256 網格，判斷「有沒有被描邊蓋到」時用的卻是浮點座標，貼著邊界的點會被歸錯邊。兩邊統一用浮點、並排除離邊界 0.002 以內的點之後，507 萬個點只剩 30 個，全集中在 B 那 1 題 |
| 窄縫：兩段邊界比線寬還近，描邊越過縫 | 300 題裡最窄的縫是 0.243，比 2 倍線寬寬 |

**順帶抓到一個錯的假設（D）**：`MiterOffset` 的註解與 006 都寫「模型的邊最短是 2，比線寬大 25 倍，偏移環不會自我相交」。
2 是**片的原型**邊長；輪廓在每個交點都被切斷，實測最短只有 **0.343**，兩端 miter 會吃掉 66%。
線寬 0.08 還沒出事，0.16 就會有四邊形打結。註解已經改掉。

**這一則留下來的通則**：

⚠️ **量測工具要跟被量的東西用同一套座標。** 3.27% 那次，量到的是工具的誤差不是 bug，
而且因為數字看起來合理，差點變成一條錯的待辦。

⚠️ **「只往外畫」這種設計前提，要去找它不成立的地方。** 002 定下這條、006 用 miter 維護它，
但兩次都只看了一般頂點。捏點是那條前提的例外，而它要等生成器開始出這種形狀才會現形。

## 011：exe 一開就讓 AMD 驅動逾時（D3D12）（2026-09-14）

**牽涉**：Player Settings 的 Windows 圖形 API（Unity 6 預設 D3D12）、Unity 6000.3.7f1 的 D3D12 後端、開發機的 AMD RX 7900 XTX（驅動 32.0.31041.1004）
**階段**：回饋收集場景第一次打包成 exe
⚠️ **這一則不是「不報錯」的那種**——它會當機。收進來是因為**猜錯的方向特別多**，那正是這份文件要留的東西。

### 原本預期

Editor 裡跑得好好的回饋收集場景，打包成 exe 之後一樣能跑。

### 實際發生

exe **一開就當**，同時跳「AMD 驅動逾時」。連 4 次、100% 重現。**Editor 不會當**；舊 build 在舊筆電上也沒事。

`Player.log` 每次都一樣：

```
回饋題單（種子 20260914）：…          ← 我們的程式跑完了
題單好了（…）                          ← 同上
d3d12: swapchain present failed (887a0005)
d3d12: Device removed reason (887a0006)   ← DXGI_ERROR_DEVICE_HUNG
d3d12: GfxDevice was not out of Local memory
```

事件記錄：`LKD_0x141_Tdr:C_AppFault_IMAGE_amdkmdag.sys-PF:1-HWS:1`（顯示驅動逾時；`AppFault`、`PF:1` = page fault）。

### 原因

**Unity 6000.3.7f1 的 D3D12 後端在開場上傳貼圖時，把還在排隊的資源提前刪掉**，GPU 讀到已釋放的記憶體（page fault），AMD 驅動逾時。
我們的 C# 沒有做不合法的呼叫——資源生命週期是引擎的責任。**D3D11 會自己管資源生命週期，所以不會出事。**

**怎麼發現的**：前面幾輪都在猜（見下面〈失敗的嘗試〉），真正的證據是開 **D3D12 除錯層**之後才拿到的：

```
d3d12 validation error (id: 921): ID3D12CommandList::Close: An ID3D12Resource object …
    was deleted prior to closing the command list.      ← 15 個資源
DRED: 81 個指令裡 78 個是 COPYTEXTUREREGION，最後 13 個 <NOT COMPLETED>
DRED GPU Page Fault VA: …
```

⚠️ **開除錯層本身就踩了兩個坑**：
1. 捷徑加 `-force-d3d12-debug` 之後回報 `could not get the debug interface (0x887a002d)`（缺少 SDK 元件）→ 要先裝 Windows 選用功能「**圖形工具**」
2. 裝了還是一樣——因為 **Unity 的 exe 自帶 Agility SDK**（build 資料夾的 `D3D12\D3D12Core.dll`，這次是 1.618.1），
   除錯層要**同版本**的 `D3D12SDKLayers.dll` 放在同一個資料夾，`System32` 那份不算。從 NuGet 的 `Microsoft.Direct3D.D3D12`（同版本）解出來放進去才開得起來

**觸發點還沒找到**：同一台機器、同一版 Unity 的**空白專案用 D3D12 不會當**，所以是我們專案裡某個空白專案沒有的東西。但下面四個嫌疑都排除了，而那 78 次複製**怎麼改都沒變少**——它們是引擎內部的上傳，不是我們的資源。

### 處理

**Windows 版圖形 API 固定 D3D11**：Player Settings → Windows → Other Settings，取消 Auto Graphics API、Direct3D11 放第一（D3D12 留第二位當備援）。
改完 exe 正常開啟，`Player.log` 確認是 `Direct3D 11.0`。專案全是 2D sprite 與 UI，用不到 D3D12。

⚠️ **不為這個升級 Unity**：比賽期間換引擎版本的風險比 D3D11 大太多。之後的 6000.3.x 修掉了幾個看起來相關的 D3D12 當機
（6000.3.9f1 的 scratch memory 配置、6000.3.17f1 的「記憶體密集操作時當機」），**但沒有一個能確定就是這一個**。
要確認的話是用專案的**複本**開新版 Unity、build D3D12 看還當不當，不動主專案。

⚠️ **另一個要知道的已知問題（UUM-137629，6000.3.16f1 修掉）**：某些硬體上，**就算圖形 API 沒有 D3D12，Player 也會在啟動時跑 D3D12 的初始化**而當掉。
我們是 6000.3.7f1，在受影響範圍內。舊筆電上跑舊 build 沒事，但**新 build 帶出去收資料前一定要在舊筆電上完整跑一輪**。

## 012：盒子進關時連抖十幾幀（Screen Space - Camera 畫布 × 改相機的回授迴圈）（2026-09-15）

**牽涉**：`BoardView`（盒子區躲開按鈕排）、`TouchInputController.IsOverBlockingArea`、畫布的 Render Mode、`RectTransformUtility.WorldToScreenPoint`
**階段**：「盒子區躲開按鈕排」第一次在 Unity 裡跑

### 原本預期

盒子區照 Inspector 上三個按鈕排的位置算一次，上緣壓到右上那排（提示／放棄）底下，之後不再變。

### 實際發生

進關時**盒子看得出來在跳**。不報錯。

加了診斷 log 之後才知道不是「跳一下」：**每一幀 `SetRule` 兩次，連續 11 幀**，上緣在 0.8974 ↔ 0.86／0.91／0.888／0.902 之間來回，越跳越小才停。
同一幀裡讀到的按鈕排位置：

| 時間點 | `ProcessButtonGroup`（右上那排）讀到的上下範圍 |
|---|---|
| 第 1 幀，進關時的第一次讀 | 2120～2320 ✅ |
| 第 1 幀，`SetRule` 改完相機之後再讀 | 1797～1886、1680～1741 ❌ |
| 第 1 幀 `LateUpdate` | 1596～1636 ❌ |
| **每一幀的 `willRenderCanvases`** | **2120～2320 ✅（從第 1 幀到第 11 幀一模一樣）** |
| 第 2～11 幀的 `Update` | 2943、2035、2162、2098、2130、2114、2122、2118、2120.7、2119.7……收斂到 2120 |

### 原因

**畫布是 Screen Space - Camera**（場景檔 `m_RenderMode: 1`）。這種畫布會跟著相機走，但**要等到畫面要畫之前（`willRenderCanvases`）才把自己搬到相機的新位置與大小**。

盒子區的換算當時是「按鈕排在世界裡的四個角 → `RectTransformUtility.WorldToScreenPoint(畫布的相機, 角)`」。
而**盒子區決定相機、相機又被拿來換算按鈕排**：

1. 讀：相機與畫布對得上 → 正確 → `SetRule` → `BoardView` **改了相機的位置與 orthographicSize**
2. 同一幀再讀（`TouchInputController.Update` 會叫 `EnsureCurrent`）：**畫布還是舊的世界座標，相機已經是新的矩陣** → 錯 → 又 `SetRule` → 相機又變
3. 畫面要畫之前畫布跟上 → 下一幀讀到的跟上一幀又不一樣……

**回授迴圈**。會收斂只是剛好每次的誤差比上一次小，不是保證。
而且每次 `SetRule` 都會發 `LayoutRecomputed` → **正在拖的片被放回原位**，所以那十幾幀裡如果有人在拖是真的會壞。

`TouchInputController.IsOverBlockingArea` 用的 `RectangleContainsScreenPoint(area, point, 畫布的相機)` 是同一種換算，
**相機剛被改過的那一幀擋片區會算錯**（按鈕旁邊點得到片、或按鈕點不到）。平常相機不動所以看不出來。

**怎麼發現的**：前兩次都在猜（見下面），第三次改成量——在三個時間點（`Update`／`LateUpdate`／`willRenderCanvases`）各印一次每個按鈕排的範圍、畫布縮放、是不是被 Layout 控制大小，只在內容變了時印。
關鍵是 **`willRenderCanvases` 那一欄每幀都一樣而且是對的**：按鈕排根本沒動，動的是換算。再加上「`SetRule` 之後同一幀讀到的立刻變了」，就是相機改完之後換算跟著變。

### 處理

新增 `UiScreenRect.TryGet`：**完全不讀相機**——把四個角換成**根畫布自己的本地座標**，照「在根畫布矩形裡的比例 × 螢幕尺寸」換成像素。
按鈕與根畫布永遠是同一個時間點的狀態，就算畫布還沒跟上相機，兩者的相對位置也是對的。Overlay 模式同樣適用；World Space 畫布退回用相機換算（它不跟相機走）。
**盒子區與擋片區共用這一份**，不再各自寫換算。

⚠️ 前提：**根畫布蓋滿整個螢幕**。相機的 Viewport Rect 改成不是全螢幕的話，Camera 模式的畫布只蓋那一塊，這個換算就錯了。

### 失敗的嘗試與被推翻的推測

| # | 推測 | 為什麼錯 |
|---|---|---|
| A | 「進關第一幀 Canvas 版面還沒算，下一幀才對，跳一格」（寫程式時就寫進註解與文件） | **沒量就寫的**。按鈕排的父物件不是被 Layout Group 排的，它的大小不用等版面重建；而且實際不是一格是十幾格 |
| B | 「`CanvasScaler` 在它自己的 `Update` 裡更新倍率，跟 `BoardView` 誰先跑未定義，改在 `LateUpdate` 再算一次就好」 | log 裡畫布縮放從頭到尾都是 1.000，而且 `LateUpdate` 讀到的一樣是錯的——**`LateUpdate` 救不了**，因為相機在 `Update` 就被改了 |

⚠️ **「會改 X 的東西，讀的時候不能經過 X」**。盒子區決定相機，所以換算按鈕位置時不能用相機——這條在寫的當下就推得出來，但當時只想到「時機」沒想到「依賴方向」。
⚠️ **兩次推測都有一個共同的破綻：沒有講清楚「是它的話 log 會長什麼樣」**。B 如果先講好「是它的話畫布縮放會在某一幀從別的數字變成 1」，一眼就推翻了。

## 013：抽屜裡的縮圖有一塊按不到（作弊鈕沒跟著退場）（2026-09-24）

**原本預期**：抽屜打開時七格縮圖都點得到，點下去把那一片拖出來。

**實際發生**：大三角那一格**上半按得到、下半完全沒反應**。不報錯、不閃爍，就是按下去什麼都沒有。在 Editor 用滑鼠也重現得出來。

**原因**：

擋片區是「按在這塊矩形上就不抓片」，而 `復原`／`清空`／`提示`／`放棄` 之所以不會擋住底下的縮圖，
靠的是**它們在抽屜打開時會自己隱藏**——隱藏中的矩形 `IsOverBlockingArea` 會跳過：

```
CanUndo = ... && !IsDragging && !IsTrayDrawerOpen && !IsLevelComplete && level.CanUndo
```

**`DebugTools` 的作弊鈕沒有這一段**。它從頭到尾顯示著，也照規矩登記了擋片區，
於是抽屜一開，它就壓在左下那一格縮圖上，蓋住的部分按下去被它吃掉。
縮圖比按鈕大，所以是「露出來的上半點得到、被蓋住的下半點不到」。

**怎麼發現的**：使用者在平板尺寸下試版面時看到的。
⚠️ **第一次的推測是錯的**——看到截圖裡片與按鈕重疊，先想到的是「暫放的片只把**視覺中心**推出障礙物，
所以片可以有一半壓在按鈕上」（`OffsetToKeepInsideAvoiding` 的註解自己就寫著「片最多可以一半在外面」）。
那條路確實存在，但**不是這次的原因**：使用者更正「是抽屜裡的縮圖」之後才對上。
查場景檔也排除了另一個候選——作弊鈕的父物件 `BoardButtonGroup` **有**在 `BoardView` 的躲避清單裡，
不是漏填。

💡 **這條是 `待辦清單.md` D 區那條技術債真的爆掉**：那裡寫的是「`DebugTools` 的按鈕要記得跟著擋片區清單走」，
但當初盯的是「有沒有登記擋片區」——**登記了反而正是它會擋的原因**，真正要跟的是「有沒有跟著隱藏」。
一條規則只做了一半，而且漏掉的那半沒有任何徵兆。

**處理**（使用者定的方向：不要每顆按鈕各自記得）：

| 做了什麼 | |
|---|---|
| 新增 `ButtonGroupVisibility` | 抽屜打開時**整排按鈕一起隱藏**。新增按鈕只要放進既有的排裡就自動受保護 |
| ⚠️ 只藏「排」，不藏「按鈕」 | 按鈕自己的顯示仍歸 `BoardActionButtons` / `PieceActionButtons`。這支去寫按鈕的話同一個欄位就有兩個寫入者，而且**作弊鈕沒有人會把它開回來** |
| ⚠️ `BoardView` 連帶改：**停用的按鈕排照躲** | 不改的話盒子區會在抽屜開闔時變大變小 → **每開關一次抽屜，盒子跟盤上的片就跳一下**。版面要穩定（不看顯示）、擋片區要跟著顯示（看顯示），兩邊需求相反是刻意的 |
| 矩形量不出來就警告一次 | 停用中的物件不會重算 layout，所以那幾排的大小**必須用 anchors 釘死**。哪天有人改成由內容決定，寬或高會量成 0 —— 那時會出聲，不會安靜地少躲一排 |

## 014：逼近搜尋的 IoU 跑出 1.016（共用邊上的格子被兩片各算一次）（2026-10-14）

**原本預期**：IoU ＝ 交集 ÷ 聯集，永遠在 0 ～ 1 之間。逼回原形狀而且對得很準時應該是 1.000。

**實際發生**：加了平移微調之後跑驗收工具（`ApproximatorTable`），數字5 的 IoU 是 **1.016**。不報錯，表上就是一個比 1 大的數字。

**原因**：

打分是「數片蓋到幾個格子中心」，判斷格子中心在不在片裡用的是**含邊上**的寫法。格子中心剛好落在兩片**共用的那條邊**上時，
兩片都把那一格算進去——同一格算兩次，交集被灌水，IoU 就會超過 1。

第一版（沒有微調）幾乎碰不到：輪廓的平移是「片的重心 − 取樣點」，很少剛好讓格子中心壓在邊上。
**平移微調把輪廓移到 1/16、1/32 這種位置**，格子中心就大量對上整數座標的邊。

⚠️ **更糟的是微調會偏好這種位置**：重複算到的格子讓分數變高，所以微調不只是「偶爾算錯」，
而是**系統性地往錯誤的方向調**。那一次實驗組的整張成績表都不能用。

**怎麼發現的**：純粹是數字不合理——IoU 的定義上限是 1。表上只有一個超過，但同一個機制在其他形狀上只是讓數字「偏高一點」，看不出來。

**處理**：

| 做了什麼 | |
|---|---|
| 落在邊上的點只算給其中一片 | 規則是邊的方向「往上，或水平往左」才算。共用的邊在相鄰兩片裡方向剛好相反，所以**恰好一片**拿到那一格（`BeamSearchContourPuzzleBuilder.OutlineRaster.ConvexContains`） |
| 驗收工具加一條斷言 | 任何一個結果的 IoU 超過 1 就直接失敗。以後再發生不會只是「表上一個怪數字」 |
| 重跑 | 修正後對照組（不微調）平均 0.896、實驗組 0.915。⚠️ **第一版當初記的 0.900 也被灌過水**（魚2 0.975 → 0.962、衣服 0.985 → 0.969），`開發進度.md` 已經更正 |

💡 「微調 0 輪 ＝ 第一版」那條日常測試在修正前後都過——經典大正方形、N = 10 剛好沒踩到。**它守的是「微調那條路沒改壞原本的路」，不保證原本的路沒有 bug**。

### 被推翻的推測

沒有。這一則是先看到數字不合理、直接推機制，推完一次就對了——但值得記的是**它差點被當成「微調很有效」的證據**：
實驗組平均 0.920、數字5 從 0.940 跳到 1.016，看起來是好消息。上限是 1 這件事是唯一的破綻。

## 015：掃描題整隻貓上下顛倒（協作者的 JSON 是 y 朝上）（2026-10-17）

**原本預期**：掃描模式逼出來的題目跟拍的貓同一個方向——頭在左上、尾巴往右上翹、腳在下面。

**實際發生**：照片對照第一次在 Unity 打開，剪影跟盒子**疊得剛好**，但**兩個都是倒的**：腳在上面、尾巴往下捲。不報錯，盒子本身看起來也只是「一個奇怪的形狀」。

**原因**：

交接文件約定的輪廓格式是「照片的像素座標、**y 朝下**」，`RecognizedContour` 照這個約定把 y 翻過來再換成模型座標（模型是 y 朝上）。
但協作者實際交的 JSON 是 **y 朝上、原點在圖的左下**（Unity 的習慣）——翻了一次就變成倒的。

**為什麼一直沒看出來**：盒子（逼近出來的題目）跟照片替身（JSON 剪影）都是從**同一份 JSON、同一套換算**來的，兩個一起倒，**彼此永遠對得上**。
驗收網頁裡那張「紅線對色塊」也是一樣：紅線跟色塊一起倒，圖本身完全合理。**只有拿去跟原本那張貓圖比才看得出來**——而照片對照的替身是剪影、不是原圖，所以要人眼認出「這隻貓是倒的」。

**怎麼確認的**：照 y 朝上換算回圖的座標（y_圖 ＝ 320 − y_JSON），點的範圍是 58～304，**正好是附圖上那隻貓的 60～300**；
原本以為「圖上那個位置是空的」、貼著右邊緣 x = 320 的那幾點，換過去就落在尾巴上。
⭐ 2026-10-14 我曾經懷疑「樣本跟附圖對不太上」，還列成要問協作者的問題——**其實就是同一件事**。檔名 `u2net_unity_contour` 本身就是線索。

**處理**：

| 做了什麼 | |
|---|---|
| `RecognizedContour` 改成照 y 朝上讀 | `PixelToModel` 不再取負號；`ImageBoundsInModel` 的左下角是像素 (0, 0)；剪影的第 row 列中心改成 y ＝ 高 − (row ＋ 0.5)（第 0 列仍然是照片最上面，轉貼圖時照樣上下對調） |
| 測試 | 「y 有翻過來」改成「**y 朝上不翻**」（直角在左下的三角形，換完還是要在左下）；整張圖的原點、剪影第 0 列兩條跟著改。逼近的驗收工具原本把外框的 y 取負號假裝成照片座標，也拿掉了 |
| 數字 | 具象題的成績**完全沒變**（驗收工具與讀檔一起改，互相抵銷）；**貓翻正之後 IoU 是 0.808／0.814**（倒著的時候是 0.823／0.833），`開發進度.md` 已經註明 |
| 交接文件 | 第二輪第 2 題改成「負責人查到了，不用回」，並請他**之後維持 y 朝上**——改了不會報錯，只會讓題目上下顛倒 |

## 016：逼近驗收裡的貓都只有軀幹（具象題的外框在捏點斷成好幾個環）（2026-10-20）

**原本預期**：驗收工具（`ApproximatorTable`）拿 25 個具象題的**整個外框**當目標，看逼近能不能把原本的形狀找回來。

**實際發生**：使用者看逼近的圖時說「**你的貓都只有抓到軀幹**」，接著自己指出「應該是具象題有捏點的問題」。四隻貓的紅線（目標輪廓）都只有身體，沒有頭和尾巴；
而且那個身體被放大到跟整隻貓一樣大。不報錯，IoU 也都在 0.86 ～ 0.89 這種「看起來還可以」的範圍。

**原因**：

驗收工具的 `OutlineOf` 把題目轉成輪廓時，**有好幾個外環就取面積最大的那個**（當初的註解寫著「有好幾個外環時取面積最大的那個；洞不管」）。
但具象題的外框在**捏點**（兩塊只碰一個點，例如貓頭跟身體）會被 `Puzzle.OuterWalks()` 切成好幾個外環：

| 外環數 | 具象題 |
|---|---|
| 3 | 貓1（20／8／4）、貓3（20／8／4） |
| 2 | 貓2、貓4（24／8）、狗2、狗3（28／4）、魚1、魚3（30／2）、數字2（14／18）、數字8（26／6）、茶壺（24／8） |

**25 個裡有 11 個**只拿到最大的那塊。`RecognizedContour` 又會把輪廓縮放到面積 32，所以軀幹被**放大**成整隻貓的大小——逼近再怎麼搜都不可能逼回原本的形狀。

**為什麼一直沒看出來**：
- 驗收網頁畫的紅線就是那個錯的目標，色塊對著它拼，**圖本身看起來合理**——要知道貓應該有頭，才會覺得不對
- 2026-10-14 看圖之後把失敗分成三類，其中「**細節被大片吃掉**（狗2 的耳朵、狗3、貓4）」與「**有洞的形狀**（數字8……）」**大半其實是這個 bug**：狗2、狗3、貓4、數字8 都在上表裡。當時把症狀歸給了演算法
- 「捏點」在這個專案不是新東西（除錯記錄 009、010），但在驗收工具寫的時候沒想到外框會在那裡斷開

**處理**：

| 做了什麼 | |
|---|---|
| `OutlineOf` 改成在捏點接成一條 | 新的 `JoinAtPinchPoints`：走第一個環走到共用的頂點 → 換走另一個環一整圈回到那個點 → 繼續走第一個環。共用點出現兩次（不相鄰），面積是各環相加，射線法判斷裡外照樣對。**遊戲本身沒有這個問題**：`OuterWalks()` 全專案只有驗收工具在用，掃描的輪廓本來就只有一條 |
| 新增日常測試 | `驗收工具的目標輪廓是整個形狀不是最大的那一塊`：每個具象題轉出來的面積都要是 32，而且至少要有一個有捏點（確認真的有測到）。變異測試：把 `OutlineOf` 改回取最大的環，這條會紅 |
| 數字 | 第三版重量：25 個具象題平均 IoU **0.923 → 0.955**、逼回原形狀 **6 → 13**（四隻貓、狗2、狗3、數字2 全部逼回來）。**之前所有的逼近成績都被低估**，`開發進度.md`〈逼近搜尋〉第一版到第三版的數字是對著錯的目標量的，已經註明 |
| 第四版的參數 | 半徑 0.75、×2 是在錯的目標上挑的，用正確的目標重掃一次（半徑 0.5／1.0、×1／×3）：照片類的形狀上預設還是最好，**不改** |
