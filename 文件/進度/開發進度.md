目前的看板是 GitHub Projects + Issues，專案名 `P0_Skeleton`，欄位 Todo / In Progress / Testing / Done。

建議沿用同一套做法，每個階段開一個 project：

- commit message 帶 issue 編號，GitHub 會自動把 commit 連到 issue —— 這同時滿足「可視性 30%」與「技術性 30%」兩項佐證

> ### ⚠️ 光寫 `#12` 不會關 issue，只會連結
>
> `#12` 這種寫法只在 issue 頁面留一條「被某某 commit 提及」，**不會改狀態**，
> 也不會把卡片移到 Done。**要關必須用關閉關鍵字**：`Closes #12`（或 `Fixes` / `Resolves`），
> 而且要 **push 到預設分支** 之後才生效。
>
> 多個要一個一個寫全：`Closes #9, closes #10`。**`Closes #9 #10` 只會關掉第一個。**
>
> 實務上目前是**手動關**的——P1-1 ～ P1-8 做完後都是上 GitHub 自己關，
> 只有 P1-7（#15）漏掉，2026-09-08 用關鍵字補關。兩種方式都行，
> 但關鍵字的好處是 issue 上會留下「被哪個 commit 關的」，那正是敏捷佐證要的連結。

### 二、設計裡「漏掉一整環」，靠查證發現

P1-9 的設計寫完、看起來完整，實際上少了**畫面同步**那一半：模型退回去了，但畫面上的片沒有人負責移動。

所以「片會跟著模型動」這個隱含假設從一開始就不成立。

| 旋轉／翻面鈕與抽屜箭頭擠在同一角 | 要真的用拇指去按才知道會誤觸 |
| 抽屜開著時按鈕蓋住縮圖 | 兩條規則各自都對，但**沒人問過它們會不會重疊** |
| 完成彈窗被盤面的片蓋住 | 四顆鈕在畫面角落，那裡剛好沒有片——**同樣的缺陷一直都在，只是沒被看見** |

第三、四條特別值得記：擋片區的清單上寫著「按鈕：有選取且沒在拖」「抽屜本體：抽屜開著」，
兩條分開看都正確，合起來才發現按鈕的矩形落在抽屜範圍裡、而且判定順序排在抽屜前面。
**這種缺陷不在任何一條規則裡面，在規則之間。**

### 三之二、⚠️「能動」不等於「對」——排序那次

彈窗蓋不住盤面時，第一個能用的修法是「把 Canvas 的 sorting order 調到比 2002 大」。
**那會動，而且五秒就能改完。**

但使用者的判斷是：**「我們應該改分層而不是一直調 order 的數字」**——那句話點破的是，
當時所有 renderer 都擠在 `Default` 層，先後全靠各自挑的數字：

| | 當時的 order | 怎麼挑的 |
|---|---|---|
| 盒子 | −1 | 「要比片小」 |
| 七片 | 0 ～ 226 | 演算法算的 |
| 抽屜、箭頭、回收框 | **2000 ～ 2002** | 「挑一個夠大的」 |
| Canvas | 0 | 預設值，沒人動過 |

**那不是排序，是巧合。** 沒有任何東西會在它被破壞時報錯，而症狀是「某個東西被蓋住了」——
跟這個專案反覆記錄的其他坑同一類。

改成 sorting layer（`Box → Piece → GameUI → CompleteUI`）之後，跨系統的先後由**一個地方**決定，
各系統的 order 只在自己那層裡有意義，抽屜那三個數字從 2000/2001/2002 縮回 0/1/2。

**這一條的價值不在技術，在於「先問這是不是真的解決了問題」**：能動的修法與對的修法差了一整個
結構，而分辨它們的成本只是多想一分鐘。

### 四、把「不報錯的 bug」變成會紅的測試

P1-9 有兩個洞是靠「先想出症狀、再寫測試」抓到的，兩個都不會丟例外：

| 洞 | 症狀（如果沒補） |
|---|---|
| undo 回到盤上時忘了清待用區旗標 | **片不見了，但過關判定認為盒子裡有它** |
| undo 送回待用區時「順手」用了記錄裡的姿態 | **undo 之後片的角度莫名其妙轉回去了** |

⚠️ 而且**驗過測試本身**：把補丁那一行改掉，確認對應的測試真的變紅。
「寫了測試」跟「測試抓得到那個 bug」是兩件事——這是 P1-1 變異測試那次留下來的習慣。

### 六、做出來之後砍掉的：吸附點視覺提示

**寫完、接上、實測、移除。** 使用者的結論是「**有吸附就有幫助了**」——
吸附本身跳過去那一下已經夠明顯，多畫兩個點只是雜訊。

⚠️ **連帶把 `SnapSolver` 為它做的改動一起還原**（多回報「最近的被拒候選」）。
砍掉提示之後那段沒有任何呼叫者，就是死程式——**跟刪 `PuzzleValidator` 同一個標準**。

**這一條的價值在於「敢刪」**：那段程式沒有錯、有測試、成本也是零，
但**沒有人用的正確程式仍然是負債**。留著它的唯一理由會是「寫都寫了」，
而那不是理由。

💡 它原本還想兼任除錯工具（「吸不上」與「附近沒錨點」在畫面上長得一樣）。
那個需求還在，但下次應該做進 `DebugOverlay` 的**文字**，不是畫在盤面上——
給開發者看的東西不該佔玩家的視覺頻寬。

### 七、把「能動」跟「該留」分開的另一個例子：滑桿

調手感時把 `SnapSettings` 從「重算時算一次」改成「每次讀都現算」，
因為原本的寫法讓 Play 模式下拉滑桿**完全沒反應而且不報錯**。

數值定了（12 / 18 dp）之後**改回原本的寫法**——那個需求是一次性的，
現算會讓「dp → 像素」每幀跑很多次。

**臨時的鷹架用完就拆**，跟 `PiecePreview` 那次是同一件事，只是這次一開始就知道它是鷹架。

|---|---|
| 1 | 找到替代路線：把盒子切成 **16 個小三角格**，就不需要布林運算 |

  （不用布林運算），**之後很可能有人重新提議**——有測試在，那個討論十秒鐘就結束
- **順帶修正了規格**：§8 原本承諾「第一、二層不需要求解器」，那個降級路線也一併作廢
- ⚠️ **也承認了一次判斷失誤**：同一天稍早才「吸附點提示做出來又刪掉」。
  這次是同一類問題（會不會被別的東西取代），但**在動手前就攔下來了**

## 用驗收句定義目標，不是用模組名

原本的完成定義是「三個模組完成並串接」。那是交付物清單不是目標。改成三句可驗收的話：

| | 驗收句 | 為什麼是它 |
|---|---|---|
| **G1** | 給一個**目標難度區間**，能在合理時間內產出落在區間內的題目 | 賣點的閉環（生成 → 難度 → 不合就丟掉重生）。少了它，「難度可控」只是宣稱 |
| **G2** | **同一題永遠得到同一個難度值**，而且有測試釘住 | ELO 的前提。它是一條不變式，不是一個功能 |
| **G3** | 生成的題目**保證有解**，且解的座標系與題目對得上 | 「保證」來自建構式生成，不來自驗證 |

⚠️ **G2 裡的「同一題」怎麼定義（2026-09-11 定案）：一題 = 形狀 + 存下來的那組參考解。**
原本隱含的定義是「一題 = 形狀」，所以難度特徵只准從輪廓算（`DifficultyFeatures` 的 XML doc 寫成硬需求）。
使用者提議從參考解拿指標（大三角暴露程度、平行四邊形在不在內部、等價交換），而那些是**拼法**的性質：
同一個形狀有好幾種拼法時，換一組解數字就變。實測預設門檻一千題裡**至少 9.7%** 保證不只一種解
（參考解裡兩個小三角剛好拼成正方形／中三角／平行四邊形，跟那一片對調就是另一種解）。

| 定義 | 能不能從解拿指標 | 代價 |
|---|---|---|
| 一題 = 形狀 | 不能 | — |
| **一題 = 形狀 + 存下來的參考解**（採用） | 能：同一題的解固定，數字就固定 | 另有其他解的那一成題目，估出來的難度可能跟玩家實際走的路不一樣 |

連帶：同一個形狀從別的路徑（別的種子、精選題）進來、帶著另一組解，會被當成**另一題**、可能有另一個難度值。
出題器自己會用 key 去重，所以同一批裡不會發生；跨批次的機率很低（兩千個形狀重複數 0）。
P2-6 若真的採用解的指標，`DifficultyFeatures` 那段「只由形狀決定」的 XML doc 要跟著改。

**當初為什麼綁形狀（2026-09-11 使用者回頭問）**：理由有兩個，份量不一樣——
① **ELO 要每題一個固定的值**：已經靠「形狀 + 存下來的參考解」解決；
② **玩家看到的只有形狀**，他要做的是「找到任何一種解」，參考解只是其中一條路。還有更容易的路時，從參考解算的難度會**高估**。
**② 是真正的代價，而且它還在。** 兩個緩解方式：
- **用玩家自己的解再算一次、跟參考解比**（使用者提議，記在 `待辦清單.md`〈局內統計與 ELO〉，當 P2-14 的延伸候選）
- **P2-11 窮舉之後多一個用途：驗證**——量同一個形狀的不同解，從解算的特徵差多少。差得不多，就證明參考解是合理的近似。
  「把所有解一起算進難度」本身不值得做：要窮舉，只能離線，而且排在 10/5 之後

⚠️ **`PuzzleSolver` 不在這三句裡。** 它服務的是中途回饋與高片數提示，兩者都可降級。
所以求解器做不完不影響交件——這件事在新的切法裡是結構上顯然的，不用每次重新論證。

## 依賴的真實形狀

```
P2-1 原語 ─→ P2-3 出題器(隨便生) ─┬─→ P2-4 玩十題
                                  └─→ P2-5 批次統計
P2-2 特徵 ────────────────────────────→ P2-6 權重與尺度
                                              ↓
                                        P2-7 照難度生
                                              ↓
                                        P2-8 串接
                                              ↓
                        P2-9 → P2-10 → P2-11 → P2-12（每一步都可以停）
```

**難度拆成兩張卡是這次重切最實質的改動**：

| | 內容 | 依賴 |
|---|---|---|
| **P2-2 特徵函數** | 凹角、角度種類、藏起來的邊 → 一組原始數字 | 無 |
| **P2-6 權重與尺度** | 原始數字 → 1200 為中心的難度值 | **需要一批題目的分布** |

原本兩件事寫在同一塊（P2-C），順序是「先做難度再做出題」。那會讓你在**還沒有任何題目**的時候
試著決定「1200 對應多少凹角」——那個數字只能猜。等出題器跑出一千題的分布，
同一個決定變成看直方圖選百分位。

### ⭐ P2-2：一個算術結果讓 `BoundaryTracer` 不用改

原規劃的 P2-15 寫「`BoundaryTracer` 第三步把內部邊丟掉了，要改成一併回傳」。
**2026-09-10 算出來那些內部邊不需要。**

七片的周長總和是固定常數（永遠是同樣那七片，剛體變換不改變邊長）。拼起來之後每一段邊
只有兩個去處：露在外面算一次，藏在裡面被兩片各算一次。所以

```
七片周長總和 = 外框周長 + 2 × 藏起來的長度
```

常數（單位：小三角的股 = 2）＝ **40 + 20√2**：

| 片 | 周長 |
|---|---|
| 大三角 ×2 | 16 + 8√2 |
| 中三角 | 4 + 4√2 |
| 小三角 ×2 | 8 + 4√2 |
| 正方形 | 8 |
| 平行四邊形 | 4 + 4√2 |

外框周長從 `Walk.Edges` 加總就有。古典大正方形驗算：(40 + 20√2 − 16√2) ÷ 2 = **20 + 2√2**。

💡 建議算 `2 × 藏起來的長度 = 40 + 20√2 − 外框周長`，兩邊留在 ℤ[√2] 裡不用碰除法
（跟 `SignedDoubleArea`、`Region` 內部的 ×2 同一招）。

⚠️ **只准用長度，不准用條數。** 長度被外框鎖死，條數沒有——同一形狀的不同拼法貼合方式不同，
總長度一樣、條數不一樣。條數是**拼法**的性質不是**形狀**的性質，用了會讓多解題目的難度值飄。

⚠️ **捏點數也不用改 `BoundaryTracer`**：捏點度數是 4，合併共線邊要求度數 = 2，
所以它一定會留在 `Walk` 裡當真正的頂點——掃一遍重複頂點就有。

**連帶**：待辦清單 D 區「`BoundaryTracer` 的內部邊沒回傳」那條技術債已消滅，P2 不動 Data 層。

#### ⚠️ 實作時第二個被推翻的判斷：洞環不必翻號

規劃階段我寫「洞環是順時針，凹凸整個相反，要小心翻號」。**寫下去之前查程式，發現是錯的。**

`BoundaryTracer` 把每條邊界邊都定向成**內部在左**（它自己的第 3 步）。洞環的有向面積確實是負的、
`IsOuter` 確實回 false，但走的時候材料一樣在左手邊——所以「**右轉 = 凹**」對外環與洞環是**同一條規則**。
而且這個性質經過 `Canonical.TransformWalk` 還在，因為它的鏡射分支會把頂點順序反轉回來。

💡 **結果是工作變少而不是變多**，而且用變異測試確認過不是矇對的：把程式改成「洞環凹凸相反」
（也就是原本以為的寫法），`洞_四個角都算凹角而且不必依繞向翻號` 當場變紅，其餘 154 條照過。

⚠️ 這一條與上面那條（周長常數）都是**「查證推翻了規劃」**，而不是實作發現的 bug。
兩次都發生在動手之前，成本是幾分鐘的查證，省下的是一次 Data 層改動與一段寫反的判斷式。

#### ⚠️ 測試自己也被修正過一次

⭐ 那條「對 16 種整體變換不變」原本只用古典大正方形。寫完才發現**正方形對 16 種變換
幾何上完全相同**，所以鏡射整段寫錯它也會過——等於沒驗。

補了一個**不對稱的 L 形**（8×6 缺一角 4×4，面積剛好 32）。它鏡射之後是另一個 L，
輪廓資料真的不一樣，但五個數字必須一樣；繞向若沒被正規化回來，凹角會從 1 變 5、
洞數會從 0 變 1，兩個都會紅。

### ⭐ P2-3：實測推翻的不是門檻，是生成策略（2026-09-10）

**這一張的敏捷佐證價值最高**，因為它是「照計畫做完 → 量一下 → 發現整個方向要改」的完整循環。

#### 一、先是門檻猜錯

審美篩選的四個門檻是憑感覺填的。第一次跑：**1027 次嘗試只中 3 題（0.3%）**，99.7% 被審美篩掉。

把門檻全開，量 300 個隨機形狀：

| 量 | 實測中位 | 猜的門檻 | |
|---|---|---|---|
| 周長 | **59.3**（最小 44.3） | ≤ 44 | ❌ **比觀測到的最小值還小，等於全部篩掉** |
| 捏點 | **4** | ≤ 1 | ❌ |
| 凹角 | 4 | ≤ 6 | ✅ |
| 洞 | 0 | ≤ 0 | ✅ |

#### 二、但真正的問題不是門檻

古典大正方形的周長是 22.6，隨機拼出來的是 44 ～ 68、捏點中位數 4。
**「隨便拼」幾乎必然生出細長、靠點接觸串起來的東西。**

原因很直接：**新的一片只要碰到任何一個節點就算合法**，而點接觸的機會遠多於邊貼合。

⚠️ **放寬門檻去接受那些形狀，等於讓審美篩選失去意義。** 所以改的是生成本身：

> **候選分兩層——先試貼著邊的，都走不通才退到只碰一點的。**

💡 判斷「貼邊還是碰點」是**免費**的：同一個擺放被幾組（錨點, 節點）湊出來，
就是它跟已放置的片重合了幾個節點——**1 個 = 點接觸，2 個以上 = 貼著一條邊**。
枚舉的時候本來就會產生這個數字。

⚠️ 這跟原本的設計相反。原本刻意去重是為了「不要讓碰到比較多錨點的擺法被抽中機率比較高」，
現在證明中性的隨機挑會生出垃圾——所以改成**明確的分層規則**，而不是靠機率偏斜。

#### 三、結果

| 量 | 改前中位 | 改後中位 |
|---|---|---|
| 周長 | 59.3 | **41.7**（最小 29.0） |
| 捏點 | 4 | **0** |
| 凹角 | 4 | 8 ⬆️（緊湊的形狀邊界比較曲折） |

門檻照實測重訂（凹角 ≤ 8、捏點 ≤ 1、洞 0、周長 ≤ 44），
**命中率 0.3% → 48.3%**，100 題只要叫 207 次、3.2 秒。

💡 **這件事本來排在 P2-5**（跑批次統計看分布）。它提早發生是因為第一次跑就撞上了——
而那正是 P2-4／P2-5 兩張「刻意提前的驗證」想達到的效果，只是這次連 P2-3 都還沒收工就先中了。

### ✅ P2-5 的結果（2026-09-10，issue #26 於 2026-09-11 關閉）

### P2-6 與 P2-12：權重先憑感覺，校正排到最後

**拼法數量不進難度公式，改當離線「對答案」的參考。**

理由：要知道有幾種拼法得把所有可能試一遍，很慢——手工題算得出來、現場生的題算不出來。
⚠️ 而「算不出來的填平均值」是這一題裡最該避開的做法：**不是偶爾算不出來，是現場生的題永遠算不出來**，
兩群題目的難度會系統性地歪向不同方向。症狀是玩家在生成題上一路贏、一碰到精選題突然爆難，
而且查不出原因（每一題單獨看都合理）。

所以分成兩邊：

| | 誰在跑 | 用什麼 |
|---|---|---|
| **遊戲裡** | 玩家的手機 | **只用形狀與參考解算得出來的特徵**（2026-09-12 修正，原本寫「只用形狀特徵」）。便宜、純函數、兩種題目同一把尺——**前提是每一題都連著一組參考解存下來**（「一題 = 形狀 + 參考解」），精選題也不例外 |
| **離線** | 開發機，做一次 | 算拼法數量，檢查形狀公式排出來的順序對不對 |

⚠️ **要老實**：沒有真人玩家資料，所以拼法數量也只是另一個猜測。
能證明的是「公式跟一個獨立算出來的東西方向一致」，**不是**「公式等於玩家的感受」。
這個定位反而更適合寫進系統概述文件。

於是 P2-6 的驗收改成四條做得到的：① 同題同值 ② 難度有高有低 ③ 排序與拼法數量同方向
④ ❌ 不宣稱等於玩家感受。

⚠️ **2026-09-12：③ 移到 P2-11／P2-12**——算拼法數量要有求解器，而求解器排在 P2-9 之後。
P2-6 自己驗 ①②④，③ 的證據是使用者在對照牆上逐列掃過的判斷紀錄（〈觀察紀錄表〉）。

💡 **權重是 `DifficultyWeights.json` 裡的數字，換權重是改檔案不是改程式**，
所以 P2-12 拖到最後甚至 P4 補都不影響交件。

#### ⭐ 二、兩個時間怎麼同時進公式

使用者的直覺是「整把 80% 都在拖的話應該能算超強」，但要排除邊拖邊想。

**不用比例，用相減**：`思考時間 = 前景 − 拖曳`，公式是 `w₁ × 拖曳 ＋ w₂ × 思考`，而 **w₂ > w₁**——
**「花在想的時間，比花在動手的時間更能說明你不會」**。
比例的三個壞性質（無單位、短時間會爆炸、⚠️ 對「很快解完」與「很慢解完」一視同仁）都避開了。

**邊拖邊想**：⚠️ **完全排除做不到**（手指在哪不告訴你腦子在做什麼），只能降低污染——
**單次拖曳超過 3 秒的部分算進思考時間**。⭐ 那個 3 秒不是亂訂的：移動本質上很快，
超過就是拿著在想；而且**之後量得出來**（回饋收集場景會給真人的單次拖曳時長分布）。

💡 **保守退路留好了**：真人資料回來發現拖曳沒有鑑別力的話，**把 w₁ 設成 0** 就退回
「只用前景時間」——改 JSON 不改程式。

#### ⚠️ 三、查程式時發現的兩件事

**① 拖曳有第二個出口。** `CancelInteraction` 接在 `boardView.LayoutRecomputed` 上，
**螢幕尺寸一變就取消進行中的拖曳**，而那條路不經過 `EndPress`。
只把「停止計時」寫在 `EndPress` 裡的話，**轉一次螢幕方向計時器就再也停不下來**，
那一局的拖曳時間會一路累加到過關，**而且不報錯**。
💡 冪等規則讓「兩個出口都叫停止」變成安全的——不用挑一邊。

**② 原本只寫了兩條冪等規則，漏了第三條。** 放棄的那一幀彈窗還沒出現
（`Update` 下一幀才跑），玩家還碰得到螢幕，剛好按下一片就會重新開始計時。
所以補上「**這一局已經結束 → 所有計時請求一律忽略**」。

#### ⭐ 四、一條免費的不變式

> **拖曳時間 ≤ 前景時間，永遠。**（背景時不可能拖曳，而前景涵蓋整關）

所以思考時間為負**在結構上不可能發生**——一旦為負就代表六個呼叫點裡有一個接錯了。

#### 一、13 個凸多邊形：自己驗證了 1942 年的定理

13 個 `puzzleKey` 全不重複，而**轉角數的分布是 3 ／ 4×6 ／ 5×2 ／ 6×4**——
正好是 Wang & Hsiung 的「1 個三角形、6 個四邊形、2 個五邊形、4 個六邊形」。
⭐ **這個分類不是對著文獻比的，是從手拼的結果獨立算出來的**，寫進系統概述文件是**可以被查核的宣稱**。

| | 難度 |
|---|---|
| 13 個的範圍 | **2124（六邊形4）～ 2404（長方形）**，正方形 2261 |
| 生成池 2000 題 | 574 ～ 1950 |

**兩條都支持 9/12 那個「當錨點、不當上限」的決定**：

1. **整族都在生成器到不了的地方**，不是只有正方形——最低的六邊形4 都比池子最高分高 174
2. ⚠️ **但難度函數對它們幾乎沒有鑑別力**：13 個只攤在 280 分內（＝1.4 個 `spread`）。
   ⭐ 更直接的證據——**有兩對的六個特徵完全一樣**（梯形1 ＝ 平行四邊形1 ＝ 2286、六邊形1 ＝ 六邊形3 ＝ 2214），
   **難度函數分不出它們是不同的形狀**。當**回歸測試的相對順序**有用，當「尺的上端」沒有意義

⚠️ **更正一條敘述**：`待辦清單.md` 原本寫「凸多邊形裡兩片大三角幾乎一定拼在一起」，
**實際是 8/13**，不是幾何必然。那句話是從正方形**一個樣本**推出來的。

#### 四、⭐ 決定：**權重不改**（而且這次是用數據決定的）

逐一特徵對「時間」的相關（個人置中，n = 56，顯著門檻約 0.29）：

| 特徵 | 現行權重 | 實測 r | |
|---|---|---|---|
| 轉角數 | 0.25 | **−0.475** | ✔ 顯著 |
| 周長 | 0.35 | **−0.380** | ✔ 顯著 |
| 錯開接觸 | 0.10 | **−0.342** | ✔ 顯著 |
| 只露一角 | 0.15 | +0.161 | 方向對，不顯著 |
| 被逼出來 | 0.15 | −0.145 | 方向對，不顯著 |
| 大三角併 | 0.15 | +0.151 | ⚠️ **量不出來**，見下 |

⚠️ **大三角併那一格不能拿來下結論**：56 題裡只有 **3 題**是 1（生成池裡只有 7%）。
單變量算出來是反的，放進多元迴歸控制掉轉角數之後又變回現在的方向——**兩種算法給相反的符號＝沒有訊號**。
要驗它得**刻意出含這個特徵的題**，照難度生的題抽不到。

**然後直接試了幾組候選權重**，看哪一組跟實際表現最合：

| 權重 | r(log時間) | r(主觀) | r(提示) |
|---|---|---|---|
| **現行** | 0.456 | 0.320 | 0.500 |
| 周長↔轉角數 對調 | 0.466 | 0.336 | 0.508 |
| 只靠轉角數 | 0.475 | 0.373 | 0.520 |
| 只靠周長 | 0.380 | 0.241 | 0.432 |

> ⭐ **最好的改動只換來 0.456 → 0.475，n = 56 下那完全在雜訊裡。**
> 而改權重的代價是整條鏈子（重算工具 → 目標範圍變 → 生成時間表重跑 → 對照牆重發布），而且**必須在錄影之前**。
> **所以這 56 筆的用途是「驗證尺」，不是「改尺」。**
>
> 論述寫成：「難度值與實際解題表現的相關經 11 人 56 題驗證，r ≈ 0.46（時間）／0.50（提示次數），**權重未因此調整**」
> ——那比調完再宣稱更硬。

⚠️ **詢答要準備的一題**：周長與轉角數彼此 **r = 0.68**，六個特徵有三個量不到獨立貢獻。
被問「六個特徵是不是有冗餘」要答得出來——答案是「目前的樣本分不開，不是它們沒有作用」。

##### ⭐ 審美那條：獎勵貼邊、減少外露周長（2026-10-21，使用者定「試審美」）

**「像」怎麼量**：看圖的問題是「柄被拼成鋸齒鏈」，鋸齒鏈的共同點是**外露周長長**（片跟片只碰一點、或只貼一小段）。所以：
- **搜尋**（`VariantBuilder.EdgeBonusPerUnit`）：beam search 每一步的分數加「新放的片跟已放的片**貼合的邊長 × 權重**」（＝獎勵藏起來的邊；兩片共線、方向相反的邊重疊的長度，浮點、容差 1e-9），`PointContactPenalty` 另外扣「只碰一點」的擺法。收尾改照這個分數排、不照 IoU。權重單位是「每 1 模型單位的貼邊換幾格」（格子 1/8），掃 4／8／16／32

# P3 難度與進度系統　⬜ 未開始（⭐ 其中一塊 2026-09-12 提前做掉了）

## ⭐ 提前做掉的：出題工具（2026-09-12，不在十五張卡裡）

**精選題庫那條線的前置。** 生成器解的是「無限題 + 難度可控」，具象題（船、貓、房子）它做不到——
`DifficultyFeatures` 那幾個數字裡沒有一個能表達「像貓」。那只能靠人拼，所以先把「拼」這件事變便宜。

⭐ **核心的取捨：不做「自由模式」，改成給一個邊長 16 的空方框。**
拿掉盒子會同時壞掉兩件事——第一片沒有錨點可吸（錨點來源是「已放置的片 ∪ 盒子輪廓」）、
`isAllowed` 沒有東西可問（合法擺放靠「在盒內」撐著）。給一個很大的框，兩件事自動成立，
**吸附／抽屜／旋轉翻面／undo／清空一行都不用改**。代價只有「第一片要先貼框邊放」，
而絕對位置本來就不入庫（鐵則三）。

| 新增 | 是什麼 |
|---|---|
| `Assets/Scenes/ToolScene.unity` | 獨立場景，**正式版的 build 不含它** |
| `PuzzleEntryToolController` | 四條檢查、命名存檔、翻頁載入舊題改。**不碰互動** |
| `LevelSession.LoadBoxOnly` | 只載入空框的 `LevelData`（沒有題目、沒有參考解） |

|---|---|---|

## ⭐ 作品定位（2026-09-10 定案，之後只往這個方向走）

> **一套空間推理的適性化訓練系統，以七巧板為載體。**
> 主要對象：**學齡前與國小低年級**。延伸對象：高齡認知訓練、特殊教育（寫成「同一套機制可沿用」，不假裝驗證過）。

**三個理由**：

1. **這是作品實際的樣子。** 真正做出來的是一台「會自己出題、也量得出使用者程度的練習機」，七巧板只是它現在裝的那組題目。**把七巧板當主角，等於把最有價值的東西講成配角。**
2. **它讓創新點自動變成產品本身。** 定位成遊戲 → 難度引擎是一個功能；定位成訓練系統 → **難度引擎就是產品**。創新性佔 30 ～ 50%，這個差別很大。
3. **證據支持**：第 30 屆 IP 組 50 件得獎作品**沒有一件是純娛樂遊戲**，但「遊戲形式 + 明確場域」有兩件拿到第一名與第二名。而「訓練／評估」的語彙會把作品推向「健康／照護／訓練」那個最大宗（16 件）的圈子——**而且不用說謊，因為它真的是**。樣態分析見上面〈歷屆得獎作品的樣態〉。

⚠️ **一條不能越的線：沒有做過成效驗證，所以只能說「訓練工具」，不能說「證實能提升空間推理能力」。**
被問到就老實答沒有，並說那是未來工作。這條線跟難度校正那條是同一個立場——
能證明的只到「公式與一個獨立算出的量方向一致」，不宣稱等於使用者的感受。
